# ログ解析(エラートリアージ + 改善提案)

ログを「見て・判断して・修正項目に落とす」を 1 コマンドで行う。目的は 2 つ:

1. **エラーの修正**: エラーログをトリアージし、修正項目を **`FIXES.md`** に落とす(**`TODO.md` には書かない** — あちらは人が管理する領域)
2. **アプリの改善**: ログ・運用データから使われ方・失敗の傾向を読み、改善案も `FIXES.md` に足す(入力データが揃い次第ここに手順を足す)

判断は台帳 `docs/error-triage.md` に fingerprint 単位で記録し、2 回目以降は**新規と再発だけ**を提示する。
経緯・設計: docs/plans/archive/log-analysis-command.md。

## 手順

### 1. 取得

```bash
./scripts/fetch-logs.sh --since 90d
```

- 出力は `.logs/<env>-<日時>/` の 1 ディレクトリ — `errors.jsonl`(エラートリアージの入力)+ `tasks.jsonl` / `tracks.jsonl` / `generation-params.json` / `settings.json` / `credits.json`(改善の気づきの入力)
- ユーザーが引数を渡したらそのまま付ける(例: `/logs --local`、`/logs --since 7d`)
- 失敗したら(g3plus-ops の `.env` 不在など)エラー内容と対処を伝えて終了
- **過去の `.logs/` ディレクトリは読まない**(毎回新規取得)
- `--local` は動作確認・デバッグ用。**台帳・FIXES の更新を伴う本来のトリアージは本番ログで行う**(ローカルのテスト起因エラーで台帳を汚さない)

### 2. 台帳と突き合わせて分類

今回の `errors.jsonl` と `docs/error-triage.md` の台帳を読み、fingerprint ごとに分類する。
日時の比較は occurredAt / lastSeenAt(UTC)を Mac のローカル時刻(`date` で確認。通常 PT)に直して行う。

| 台帳の状態 | 分類 |
|---|---|
| (行が無い) | **新規** — 調査対象 |
| 修正済み で、修正日より後に発生がある | **再発** — 調査対象(再オープン) |
| 様子見 で、判定日より後に発生がある | **様子見の継続** — 再判定(継続 or 昇格) |
| 対応中 | `FIXES.md` を確認。対応項目が実施済み(`[x]`)なら **修正済み** 化(修正日 = 実施コミットの日付) |
| 無視(または上記の発生条件に該当しない既知) | 件数だけ集計 |

### 3. 新規・再発・継続だけ調査

- `source` / `event` から発生箇所を特定する。server は `server/src/` で `logError` / `logWarn` の呼び出しを grep、iOS(`ios-*`)は `ios/DailyAIMusic/Sources/Services/` を見る
- 呼び出し元のコードを読み、`message` / `detail`(errorCode・path・stack 等)と突き合わせて原因の当たりを付ける
- `tasks.jsonl` の FAILED とも突き合わせる — **エラーログ導入(2026-08-11)前やサーバー再起動中の失敗は error_logs に残らず、タスク側にしか出ない**。同種の失敗が過去にもあれば頻度の判断材料になる
- 推奨判定を決める(下記「判定の目安」)

### 4. 適用(まとめて書き込む)

判定を確定し、以下をまとめて行う。**実害の有無や優先度が判断できず迷うものだけ、書き込む前にユーザーへ確認する**(それ以外は確認を待たない)。

1. 修正・改善項目を `FIXES.md` へ追記(fingerprint と日付を併記)。**`TODO.md` には書かない**
2. `docs/error-triage.md` の台帳を更新(新規行の追加、状態・判定日・修正日・メモの更新)
3. 変更を 1 コミット(例: `ログ解析: 新規 2 件を判定(FIXES 追加 1・無視 1)`)

### 5. 報告

- 冒頭 1 行サマリ: `新規 X / 再発 Y / 様子見の継続 Z / 既知(無視・対応中)N 件`
- 判定ごとに: fingerprint・`origin/source/event`・件数と最終発生・原因の当たり・判定と根拠。`FIXES.md` に足した項目はその文面も示す
- エラー個別の判定に加えて、**傾向から見えた改善の気づき**(頻度の偏り・特定画面や API への集中・仕組み側の不備など)があれば添える
- **新規・再発・継続がゼロなら 1 行サマリだけで終了**(台帳も FIXES も触らない)

## 判定の目安

- **ノイズ → 無視**: 外部スキャナ由来の `api/unauthorized`、iOS の `-999 cancelled`(SwiftUI の画面遷移による正常なリクエストキャンセル)など、コードの不具合でも運用の問題でもないもの。**収集側で拾わない修正が可能なら、その改善を `FIXES.md` に足してから**無視にする(台帳で黙らせて終わりにしない)
- **一時的 → 様子見**: ネットワーク起因の単発 `transport_failed` / `fetch_failed`、単発の `web_search_failed` など、再現するか分からないもの。判定日を入れておくと以降の発生だけが再提示される
- **バグ → FIXES 追加(対応中)**: `decode_failed`(サーバーとアプリの契約ずれ)、`task_failed` / `daily_failed` / `plan_issue_remains` の反復、同一 fingerprint の急増。`FIXES.md` に追記し、台帳のメモに項目名を書く

## FIXES.md の書式

- 1 項目 1 チェックボックス。`— 根拠(件数・日付・fingerprint)` と対策候補を添える
- 実施したら**削除せず `[x]` にして残す**(次回の `/logs` が台帳の「修正済み」化に使う)
- 着手するときは通常の作業着手ルール(プラン作成 → 実装)に乗せる

## 台帳の書式(docs/error-triage.md)

| 列 | 内容 |
|---|---|
| fingerprint | `error_logs.fingerprint`(12 桁) |
| 状態 | `無視` / `様子見` / `対応中` / `修正済み` |
| 判定日 | 最後に判断した日(YYYY-MM-DD、ローカル時刻) |
| 修正日 | `修正済み` のみ。再発判定の基準日 |
| 分類 | `origin/source/event` |
| 内容 | message の代表例(1 行) |
| メモ | 判断の理由。`対応中` は FIXES 項目への言及、`修正済み` は対応したコミット等 |
