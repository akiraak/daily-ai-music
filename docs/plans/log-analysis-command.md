# ログ解析を 1 コマンド化する(`/logs`)

> 2026-08-13 改名: 当初は「エラーログのトリアージ(`/errors`)」として作ったが、エラー修正だけでなく
> **ログからアプリの改善案を出す**用途にも使うため `/logs` に広げた。エラートリアージは
> その最初の実装で、改善提案の解析は入力データが揃い次第このコマンドに足していく。

## 目的・背景

エラーログの収集・保存・取得(error-log-collection の Phase 1〜3)は 2026-08-11 に導入済みで、`scripts/fetch-error-logs.sh` で `.logs/` に JSONL が落ちる。しかし**溜まったログを「見て・判断して・タスク化する」手順が無い**。

今のままだと毎回「fetch → 目視 → 判断」を繰り返すことになり、一度「これは外部スキャナのノイズ」と判断した `api/unauthorized` のようなエラーを次回もまた見直すことになる。判断の記録が残らないのが問題の中心。

ゴール: **`/logs` の 1 コマンドで「取得 → 新規/再発の抽出 → 原因の当たり付け → TODO 追記 → 判断の記録」まで完結**する。2 回目以降は判断済みのエラーが再提示されず、新しいものだけを見ればよい状態にする。エラー個別の判定に加え、傾向から見えた**改善の気づき**(頻度の偏り・仕組み側の不備)も同じ実行で提示する。

## 決めたこと(方針)

| 論点 | 決定 |
|---|---|
| 形態 | **スラッシュコマンド**(`.claude/skills/logs/SKILL.md`)。定期実行にはしない(理由は下記) |
| 名前 | `/logs`(エラー専用ではなく、ログ解析全般の入口にする) |
| 既知/新規の判定 | **台帳ファイル `docs/error-triage.md`**(git 管理)に fingerprint ごとの判断を記録し、次回以降の差分の基準にする |
| 取得 | 毎回 `./scripts/fetch-error-logs.sh --since 90d`(サーバーの保持期間と同じ範囲)。差分はサーバー側でなく**ローカルの台帳との突き合わせ**で取る。`.logs/` の過去ファイルは入力に使わない(重複していて紛らわしい) |
| `--local` の扱い | 動作確認・デバッグ用。台帳・TODO を更新する本来のトリアージは本番ログで行う(ローカルのテスト起因エラーで台帳を汚さない) |
| 原因の当たり付け | Claude Code が `event` → 発生箇所のコード(`logError`/`logWarn` の呼び出し元)を読んで推定する。ここがコード読解そのものなので、サーバー側に解析機能は作らない |
| タスク化 | `TODO.md` へ追記(fingerprint を併記して台帳と突き合わせられるようにする) |
| 適用 | **提案 → 人が承認 → 書き込み → コミット**。無人で TODO.md を書き換えない |

### なぜスラッシュコマンドか(定期実行でなく)

- 原因の当たり付けはコード読解そのもので、リポジトリを開いた Claude Code セッションでやるのが一番精度が高い
- 判定(無視/様子見/タスク化)には人の確認を挟みたい。無人実行だと TODO.md がノイズで膨れ、信用されなくなる
- 本番の `API_SECRET` は Mac(g3plus-ops)にしかなく、無人実行は実行環境の用意から必要になる
- ログ量が少ない(90 日で数十行想定)。毎日回す価値がない
- 件数が増えて「気づくのが遅い」が起きたら、**「新着 fingerprint 数を通知するだけ」の軽い定期実行**を後から足せばよい。台帳はそのまま流用できる
- ターミナルからワンショットで走らせたいときは `claude "/logs"`。取得とサマリだけなら `./scripts/fetch-error-logs.sh` 単体で足りる(Claude 不要)

### 台帳(`docs/error-triage.md`)

fingerprint ごとに 1 行の表。人が読めて、手でも直せて、git で判断の履歴が残る。

| 列 | 内容 |
|---|---|
| fingerprint | `error_logs.fingerprint`(12 桁) |
| 状態 | `無視` / `様子見` / `対応中` / `修正済み` |
| 判定日 | 最後に判断した日(YYYY-MM-DD、ローカル時刻) |
| 修正日 | `修正済み` のみ。再発判定の基準日 |
| 分類 | `origin/source/event` |
| 内容 | message の代表例(1 行) |
| メモ | 判断の理由。`対応中` は TODO 項目への言及、`修正済み` は対応したコミット等 |

状態と再浮上のルール:

| 状態 | 次回実行時の扱い |
|---|---|
| (台帳に無い) | **新規**: コードを調査して判定を提案 |
| 無視 | 再提示しない。サマリに件数だけ出す(急増していれば気づける) |
| 様子見 | 判定日以降に発生があれば再提示(継続 or 昇格を判断) |
| 対応中 | 対応する TODO 項目が `DONE.md` に移っていたら `修正済み` 化(修正日付き)を提案 |
| 修正済み | 修正日以降に発生があれば **再発** として再オープンを提案 |

### `/logs` の流れ(SKILL.md に書く手順)

1. `./scripts/fetch-error-logs.sh --since 90d` を実行(引数で `--local` や期間を上書き可。g3plus-ops の `.env` が無ければその旨を案内して終了)
2. 取得した JSONL と台帳を突き合わせ、fingerprint を「新規 / 再発 / 様子見の継続 / 既知(無視・対応中)」に分類
3. **新規・再発だけ**調査する: `event` から発生箇所のコードを読み、原因の当たりを付けて推奨判定(無視 / 様子見 / タスク化)を決める
4. 結果を一覧で提示(件数・最終発生・原因の当たり・推奨判定)。傾向から見えた改善の気づきも添える。承認は一括、個別の変更も可
5. 承認後にまとめて適用: タスク化分を `TODO.md` へ追記 + 台帳を更新 + **1 コミット**
6. 新規・再発ゼロなら「新規なし(無視 X 件・様子見 Y 件で発生継続)」の 1 行サマリで即終了

### 判定の目安(SKILL.md に書く基準)

- **ノイズ(無視)**: 外部スキャナ由来の `api/unauthorized`、iOS の `-999 cancelled`(SwiftUI の画面遷移による正常なリクエストキャンセル)等。**収集側で拾わない修正が可能ならそれをタスク化してから**無視にする(台帳で黙らせて終わりにしない)
- **一時的(様子見)**: ネットワーク起因の単発 `transport_failed` / `fetch_failed`、単発の `web_search_failed`
- **バグ(タスク化)**: `decode_failed`(サーバーとアプリの契約ずれ)、`task_failed` / `daily_failed` / `plan_issue_remains` の反復、同一 fingerprint の急増

現在の本番ログ(初回実走で 14 fingerprint・発生 75 件)がそのまま初回の題材になる: kie.ai の style 語彙拒否による毎日生成の失敗、Anthropic クレジット不足、iOS の `-999 cancelled` ノイズ(全発生の過半)、デプロイ順序ずれによる一時的な 400 など。

## 対応方針(Phase)

### Phase 1: 仕組みを作る

1. `.claude/skills/logs/SKILL.md`(新規): 上記の流れ・判定の目安・台帳の書式を手順として記述
2. `docs/error-triage.md`(新規): 空の台帳(表ヘッダ + 状態・再浮上ルールの短い説明)

### Phase 2: 実ログで初回トリアージ

1. 本番ログで `/logs` を実走し、fingerprint を判定して台帳の初期状態を作る(`-999` の報告除外など、収集側の改善タスクが出たら `TODO.md` へ)
2. 実走で分かった手順のずれを SKILL.md に反映
3. 後片付け: `CLAUDE.md` のエラーログ節に `/logs` を追記、`TODO.md` → `DONE.md`、本プランを `docs/plans/archive/` へ

## 影響範囲

- 新規: `.claude/skills/logs/SKILL.md`、`docs/error-triage.md`
- 変更: `CLAUDE.md`(エラーログ節)、`TODO.md` / `DONE.md`
- **サーバー・iOS のコードには触らない**(トリアージが生んだ改善タスクは別タスクとして実施)

## テスト方針

Phase 2 の実走がそのままテスト。確認観点:

- 取得〜提案まで人手ゼロで進み、承認 1 回で TODO.md・台帳・コミットまで完了する
- 2 回目の実行で、判定済みの fingerprint が再提示されない(1 行サマリで終わる)
- 台帳を手で `修正済み`(過去の修正日)にした fingerprint が「再発」として検出される
- ログ 0 件・fetch 失敗(g3plus-ops の `.env` 不在)で分かるメッセージが出る

## 未確定事項

- **改善提案(エラー以外のログ・データの解析)** — アプリの使われ方や生成の傾向(`tasks` の成功率・LLM トークン・生成時間、公開ページのアクセス等)から改善案を出す手順。何を入力にするかを決めてから `/logs` に手順を足す(収集の仕組みが必要ならそれも別タスク)
- fingerprint がパス・エラー文言ごとに分かれる(初回実走で cancelled が 3 つ、unauthorized が 4 つに割れた)— 台帳が細かく増える。今は台帳側でまとめて判定すれば足りるが、煩わしくなったら収集側の正規化を検討
- 台帳との突き合わせを決定的にする小スクリプト(`scripts/triage-errors.mjs` 等)— まずは SKILL.md の手順だけで運用し、分類ミスや取りこぼしが出たら足す
- 新着 fingerprint 数だけ知らせる定期実行(通知)— ログ件数が増えて「気づくのが遅い」が起きたら検討
- 管理画面へのエラー一覧表示 — 引き続きスコープ外(error-log-collection から継続)
