# アーティストから生成・曲名から生成の UI 整理と再構築

作成: 2026-08-12

## 目的・背景

TODO「アーティストから生成と曲から生成のUIが分かりにくいので整理して再構築」の実施プラン。

現状の生成まわりの入口は iOS の生成タブに集約されている:

```
生成タブ
├── おまかせ生成(POST /api/daily/run)
├── 生成パラメータ(読み取り専用)
├── 曲名から生成 → 曲検索 → 候補選択 → [アーティスト登録(200 曲取り込み)+ 曲の有効化 + 生成] を 1 タップで実行
├── アーティストから生成 → アーティスト一覧(追加・再取得・削除)
│                          └── 曲一覧(絞り込み・有効/無効トグル・一括操作・タップで生成)
└── 進行状況
```

### 分かりにくさの正体

1. **名前と中身の乖離** — 「アーティストから生成」の実態はアーティスト管理(登録・再取得・削除)+ 参照曲管理(有効/無効・一括操作)であり、生成はその最深部の 1 タップだけ。参照曲の有効/無効を整えたいだけでも「〜から生成」という導線をたどることになる
2. **「曲名から生成」の大きな副作用** — 曲を 1 曲選んだつもりが、アーティストの逆引き登録(最大 200 曲の取り込み)まで走る。逆に「曲名から参照曲を登録したいだけ」の経路は無い(必ず生成まで進む)
3. **2 つの入口の違いが「目的」でなく「探し方」** — どちらも最終的には「参照曲を 1 曲選んで生成」する同じ機能なのに、入口が検索経路の違い(曲名 / アーティスト名)で分かれ、それぞれに管理機能が混ざっている
4. **曲一覧の 1 行に 2 つの意図** — タップ = 生成、行末トグル = 有効/無効。「候補にする」と「今すぐつくる」という別の操作が同じ行に同居し、誤タップで生成確認が出る

## 機能分解(確認)

「生成 / アーティスト / 楽曲」という分解が妥当かの確認。洗い出すと:

| 領域 | 機能 |
|---|---|
| **生成**(曲をつくる) | おまかせ生成(daily: サーバーが参照曲を選ぶ)/ 曲を選んで生成(artist: 人が参照曲を選ぶ。管理画面は追加の要望も指定可)/ 進行状況 / 生成パラメータ / 残クレジット |
| **アーティスト**(参照元の登録・管理) | iTunes 検索(アーティスト名 / 曲名の 2 経路)→ 登録(最大 200 曲取り込み)/ 再取得 / 削除 |
| **楽曲 = 参照曲**(候補の管理) | 有効/無効(個別・一括)/ 絞り込み・表示フィルタ |

**結論: 分解は妥当。ただし 2 点の注意がある。**

- **「楽曲」という語は生成済みの楽曲(ライブラリ / 管理画面の楽曲一覧)と衝突する**。この領域が指すのは `artist_songs`(生成のもとにする既存曲)なので、UI 上は「参照曲」と呼び分ける
- **アーティストと参照曲は独立した 2 領域ではなく 1:N の階層**(取り込みがアーティスト単位のため)。UI 上は「アーティスト一覧 → その人の曲一覧」の階層 1 領域にまとめるのが自然で、実質は **「生成(つくる)」と「参照曲の管理(アーティスト + 曲)」の 2 領域** + 既存のライブラリ、と捉え直せる

現 UI の問題は、この分解でいう「参照曲の管理」が丸ごと「生成」の入口の下にぶら下がっていること、そして「曲名から生成」が 3 領域(登録 + 有効化 + 生成)を 1 タップに合成していることに尽きる。

## 対応方針

原則: **「生成」を名乗る入口は生成だけにし、参照曲の管理(アーティスト登録・有効/無効)を独立した領域として分離する**。

### iOS(構成は Phase 0 のモックで決定)

**案 1(推奨): 参照曲を独立タブに(4 タブ化)**

```
ライブラリ / 生成 / 参照曲 / 設定
```

- **生成タブ**: おまかせ生成(主役・現状のヒーローを維持)+ **曲を選んで生成**(有効な参照曲の横断リストから検索して選ぶ → 確認 → 生成)+ 進行状況 + 生成パラメータ + クレジット。「アーティストから / 曲名から」という探し方の分岐を入口から消し、生成の経路を「おまかせ / 曲を選ぶ」の 2 本に整理する
- **参照曲タブ**: アーティスト一覧 → 曲一覧(有効/無効・一括操作)。追加はアーティスト名 / 曲名の 2 経路を 1 つの検索 UI に統合(管理画面の「登録」パネルと同じ切替式)。曲一覧の行アクション「この曲で生成」は残すが、主目的は管理で生成は従(現状の主従を逆にする)
- 「知らない曲をその場で登録して即生成」の一気通貫は、「曲を選んで生成」画面に「登録済みにない曲は曲名で探して追加」の導線を置き、登録後にそのまま生成確認へ続けて維持する

**案 2: 3 タブのまま生成タブ内を直す**

- タブは増やさず、生成タブの導線を「曲を選んで生成」(生成)と「参照曲の管理」(管理)の 2 行に改名・整理する。変更が小さい代わりに、管理領域が生成タブの下に残る

### サーバー API

- 「曲を選んで生成」の横断選択用に **`GET /api/reference-songs`(有効な参照曲の全アーティスト横断一覧。アーティスト名付き・`term` での絞り込み対応)を追加**。既存はアーティスト単位の `GET /api/artists/:id/songs` しか無く、クライアントで全アーティストを引くと N+1 になるため
- 生成・登録・有効/無効の既存 API は変更しない(UI の組み替えのみ)

### Web 管理画面

- iOS ほど階層が深くなく混乱は小さいので、**iOS で決めた名前・文言・構成に追従する程度に留める**(例: パネル見出しと説明文の統一、「この曲で生成」の位置づけ)。ページ分割(参照曲ページの独立)まで踏み込むかは Phase 0 の決定に合わせる

### スコープ外

- 生成経路(`daily` / `artist`)やデータモデルの変更 — UI の組み替えのみ
- 取り込み既定無効・有効化の仕様変更 — 現仕様([docs/specs/music-generation.md](../specs/music-generation.md))のまま
- ライブラリ(生成済み楽曲)側の変更

## テスト方針

実生成はコストが掛かるため行わない(生成 API は受付 201 が返るところまで)。

- `npm run typecheck` と新 API の隔離 DB(`sqlite3 .backup` + `daily_enabled=false`)での確認
- iOS: シミュレータビルド + XCUITest スモーク(一覧 → タップ → 再生の既存テストが構成変更後も通ること。生成導線の identifier 変更に追従)
- 管理画面: ヘッドレス Chrome でスクリーンショット確認(横幅 500px 以上)
