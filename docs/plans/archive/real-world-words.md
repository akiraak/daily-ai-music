# リアルワード: 外部リソースから曲の着想ワードを作り、重複を防ぐ

旧プラン「外部リソース(ニュース・天気)参考生成」と「アイデアワード使用制限」を 1 本の
処理フローに統合したプラン。

- **名称**: UI 表示は「リアルワード」、コードは `real_world_words`(テーブル)/
  `realWorldWords`(TS フィールド)/ `RealWorldWord`(型)
- **旧プラン**: `external-context-generation.md` / `idea-word-usage-limit.md`(本プランに統合し削除)

## 目的・背景

毎日の自動生成は現在、プリセットプール+好みプロファイル+直近スタイル(重複回避)だけを
LLM に渡しており、「その日ならでは」の要素が無い。また重複回避も「直近 5 件のスタイル文字列を
渡して『避ける』と指示」するだけ(`db.listRecentStyles`)で、ワード単位の管理が無く、
似たテーマの曲が連続しやすい。

そこで両者を 1 つの流れにする:

```
外部リソース取得(ニュース・天気)
  → プロンプトに「今日のコンテキスト」として注入
  → LLM が SongPlan と同時に「リアルワード」(その曲の中心となった語)を出力
  → real_world_words テーブルに保存
  → 次回生成時、直近ウィンドウの使用回数を集計してプロンプトで制限
     (同一ワードは直近 30 日で 2 回まで。古いワードは自動で再利用可能に)
```

外部リソース由来のテーマ語もリアルワードとして記録されるため、
「同じ時事テーマが続く」ことへの抑制にもなる。

## 対応方針

### 1. 外部コンテキストの取得と注入

- 新モジュール `server/src/context.ts` に「コンテキストソース」を並べる。各ソースは
  `{ name, enabled 判定, fetch(): Promise<string | null> }` の小さな関数で、失敗したら null
  (**外部取得の失敗で毎日の生成を止めない**。タイムアウト数秒+エラーは警告ログのみ)
- `runDaily()` で `generateSongPlan` の前に全ソースを並行取得し、得られたものだけを
  `## 今日のコンテキスト(歌詞・曲調の着想に使う。ニュースの報告ではなく、雰囲気やテーマとして
  さりげなく織り込む)` セクションとしてプロンプトに追加する(`llm.ts` に `extraContext?: string`
  を足すだけ)
- 追加の LLM コールはしない(見出し・天気をそのまま渡し、選別・消化は既存の
  generateSongPlan の 1 コールに任せる)
- 注入内容は既存の `tasks.llm_prompt`(LLM 入力全文)に記録されるので、
  管理画面の楽曲詳細から「その日何を参考にしたか」を確認できる
- ソース:
  - **ニュース**: Google News RSS(日本版トップニュース、キー不要)
    `https://news.google.com/rss?hl=ja&gl=JP&ceid=JP:ja`。代替: NHK ニュース RSS。
    見出し+概要を上位 5〜8 件に整形して渡す。LLM には「1 つ選んで雰囲気・テーマとして
    織り込む(時事の固有名詞を歌詞に直接入れない)」と指示。重い事件・訃報を
    そのまま曲にしない緩衝はこの「さりげなく」指示で吸収する
  - **天気**: Open-Meteo(キー不要・無料)で当日の天気・気温 → ムード/テンポの着想に。
    位置は `settings` に緯度経度で持つ(既定: 東京)

### 2. リアルワードの生成・保存

- `SONG_PLAN_SCHEMA` に `realWorldWords: string[]` を追加し、LLM 自身に
  「今日のコンテキストから採ったテーマ語+この曲の中心要素(ジャンル・ムード・情景など)を
  英語小文字で 5〜8 個」出力させる(追加 LLM コールなし)
- 新テーブル `real_world_words(id, task_id, word, created_at)` に保存
  (後方互換マイグレーション。既存タスクは対象外でよい)
- 管理画面の楽曲詳細に「リアルワード」として表示

### 3. 使用回数の制限

- 生成前にウィンドウ内(既定 30 日)のワードを集計し、プロンプトに追加:
  - 使用 2 回以上 → 「## 使用禁止ワード(直近で使いすぎ。テーマ・スタイル・歌詞の中心に据えない)」
  - 使用 1 回 → 「## 残り 1 回のワード(できれば別のアイデアを優先する)」
- 期限切れはクエリを `created_at >= now - ウィンドウ` で絞るだけ(物理削除は不要。
  気になれば起動時にウィンドウ外を purge)。ウィンドウを外れたワードは自動的に再利用可能になる
- **検証リトライ**: 返ってきた `realWorldWords` に禁止ワードが含まれていたら、指示を強めて
  1 回だけ再生成する(それでも含まれたら警告ログを出して採用 — 生成を止めない)

### 4. 設定(settings テーブル)

- `context_news` / `context_weather`: ソースごとの ON/OFF。生成時に毎回読むため切替は
  次の生成から即座に効く(サーバー再起動不要)
- `weather_lat` / `weather_lon`: 天気の位置(既定: 東京)
- `word_max_uses`: ウィンドウ内の同一ワード使用上限(既定 **2**。ハードコード開始、UI は必要になったら)
- `word_window_days`: ウィンドウ日数(既定 **30**。毎日 1 曲+手動なので約 30〜40 曲分)
- `GET/PUT /api/settings` のレスポンス・検証に上記を追加

### 5. パラメータ設定画面(管理画面に新設)

- **`server/public/settings.html` + `settings.js`**(パラメータ一覧ページと同じ独立ページ構成。
  ヘッダーのナビリンクでトップ・パラメータ一覧と相互リンク)
- 表示・操作:
  - **外部ソース**: ニュース ON/OFF トグル、天気 ON/OFF トグル、天気の位置(緯度経度)
  - **毎日の自動生成**: dailyEnabled / dailyHour / dailyTimezone / adventureProbability
    (現状 UI が無いのでこの画面に同居させる。API は既存のまま)
- 変更は `PUT /admin/api/settings` で即保存し、保存結果を反映表示(専用の保存ボタンは置かず
  トグル操作で即時保存。評価ボタンと同じ操作感)

### 適用範囲

- 外部コンテキストの注入は毎日の自動生成(runDaily)のみ。iOS・`POST /api/generate`(manual)は
  注入なし
- リアルワードの保存・使用制限は daily / daily_adventure / manual の全モードに適用する
  (generateSongPlan 内で一元処理)。manual はユーザーの自由リクエスト・選択プリセットが
  最優先である旨を既存どおり維持し、ユーザー指定と禁止ワードが衝突した場合は
  ユーザー指定を優先すると明記する
- 既存の `recentStyles`(直近 5 件のスタイル全文)は当面併用し、ワード制限が機能することを
  確認できたら削除を検討する

### Phase 構成

- **Phase 1: 注入基盤 + ニュース + パラメータ設定画面** — `context.ts` の枠組み、
  `generateSongPlan` へのセクション注入、Google News RSS、settings.html / settings.js 新設
  (ニュース ON/OFF・毎日の自動生成セクション)
- **Phase 2: リアルワードの生成・保存** — スキーマ追加(`realWorldWords`)、
  `real_world_words` テーブル+マイグレーション、保存処理、楽曲詳細に表示
- **Phase 3: 使用制限** — 集計+プロンプト注入+検証リトライ、設定キー
- **Phase 4: 天気** — Open-Meteo、設定画面に天気 ON/OFF・位置入力を追加
- **Phase 5: 可視化(任意)** — パラメータ一覧ページに「直近のリアルワードと残り回数」を表示

### モデル精度の確認と Opus 5 への切替判断(稼働後チェック)

現行 LLM は `claude-sonnet-5`(既定。$3/$15 per MTok)。Phase 1〜3 の稼働後に数日分の生成を
管理画面で確認し、リアルワードの質(曲の中心要素・今日のコンテキストを的確に拾えているか)と
禁止ワードの遵守率が悪ければ `.env` の `LLM_MODEL` を **`claude-opus-5`**($5/$25 per MTok)へ変更する。

- どちらのモデルも構造化出力(`output_config.format` の json_schema)対応のためコード変更は不要
  (`llm.ts` は `LLM_MODEL` を参照、使用モデルは `tasks.llm_model` に記録済みで前後比較が可能)
- チェック観点: ① realWorldWords が style / 歌詞・今日のコンテキストの実内容と一致しているか
  ② 禁止ワード混入時のリトライ発生頻度(警告ログ)③ styleJa / lyricsJa の訳質

## 影響範囲

- `server/src/context.ts`(新規)、`scheduler.ts`(runDaily でコンテキスト取得)、
  `llm.ts`(`extraContext` 受け取り、スキーマ+制限セクション注入+リトライ)、
  `db.ts`(テーブル・集計クエリ)、`generation.ts`(realWorldWords 保存)、
  `index.ts`(settings 検証、tasks/tracks API に realWorldWords 追加)
- `settings`(キー追加のみ。スキーマ変更なし)、DB は `real_world_words` テーブル追加
- 管理画面: `settings.html` / `settings.js`(新規)、`index.html` / `presets.html`
  (ナビリンク追加、楽曲詳細・パラメータ一覧の表示追加)
- iOS は変更なし(API 追加フィールドは無視される)

## テスト方針

- 各 Phase: `npm run typecheck`
- Phase 1・4: コンテキスト取得関数の単体実行(実 RSS/API を叩いて整形結果を目視)。
  失敗系: 到達不能 URL に差し替えてもプロンプト組み立てが従来どおり成功する
  (セクション無しになる)こと
- Phase 2・3: 隔離 DB で保存・集計(2 回使用 → 禁止入り、ウィンドウ外 → 復活)の単体検証
- 設定画面: ヘッドレス Chrome で表示確認 + トグル切替が `GET /admin/api/settings` に反映されること、
  OFF にしたソースのセクションがプロンプト組み立てに入らないこと
- E2E(実生成・クレジット消費)は Phase 3 完了時に管理画面の生成ボタンで 1 回実施し、
  楽曲詳細の LLM 入力全文に「今日のコンテキスト」・禁止ワードセクションが入ること、
  realWorldWords が保存され歌詞に反映されていることを確認
