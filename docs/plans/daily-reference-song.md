# 毎日の自動生成を参照曲ベースに変更(実装プラン)

## 目的・背景

毎日の自動生成(`daily` / `daily_adventure`)は、プリセット要素プール + ニュース見出しから LLM が自由にスタイルと歌詞を組む方式。一方 2026-08-09 に入れた**参照曲ベースの生成**(`artist`)は、`web_search` で実際の曲情報(BPM・キー・コード進行・楽器編成・ボーカル)を調べてから style を書くため、生成物が「なんとなくそれっぽい音楽用語の羅列」ではなく実在の曲の構造に裏付けられる。ただし手動の入口(管理画面・iOS の「アーティストから生成」「曲名から生成」)からしか使えない。

毎日の曲をこちらに乗せ替える。`llm.ts` の web_search 有効化条件は**モード名ではなく `referenceSong` の有無**で判定するようすでに作ってあるため(2026-08-09 の設計判断)、参照曲を渡せば検索はコードを変えずに効く。実際の作業は「誰がどの曲を選ぶか」と「同期のままだと本番で必ずタイムアウトする `POST /api/daily/run` の非同期化」が中心になる。

## 決めたこと(2026-08-10、ユーザー確認済み)

| 論点 | 決定 | 理由 |
|---|---|---|
| 切り替え範囲 | **1 日の全曲を参照曲ベースにする**。登録曲が 0 件のときだけ現行のプリセット方式へフォールバック | TODO の文面どおりの素直な切り替え。プリセットの 👍/👎 学習ループは daily から外れるが、その後始末は別 TODO(「毎日更新が曲参照になったのでそれ以外の機能を洗い出して削除する」)で扱う |
| 曲の選び方 | **サーバーが選ぶ**(LLM には選ばせない) | 実装が最も単純で、出力スキーマの追加も照合も要らない。深いカット・ライブ版を引くリスクは下記のノイズ除外と LRU で緩和する |
| 今日のコンテキスト(ニュース) | **注入する**(既存の `context_news` 設定を尊重) | 曲調は参照曲に寄せつつ歌詞のテーマは今日のニュースから採る。「毎日違う曲が届く」性格とリアルワード制限の意味が保たれる |
| 冒険日 | **daily からは外す**(参照曲ベースの経路では判定しない。`mode` は `daily` 固定) | 「参照曲に似せる」目的と「大きく外す」指示が矛盾するため。`adventure_probability` はフォールバック経路でのみ生きる |

## 対応方針

### 1. 参照曲の選択(サーバー側)

新規 `server/src/reference.ts` に、候補の取得(db 経由)と選択(純関数)を置く。

**候補の取得** — `db.listReferenceCandidates()` を追加(スキーマ変更なし。`tasks.artist_song_id` は 2026-08-09 に記録だけ先に用意してある)。

```sql
SELECT s.id, s.artist_id, s.title, s.album, s.release_year, s.genre, a.name AS artist_name,
       (SELECT MAX(t.created_at) FROM tasks t WHERE t.artist_song_id = s.id) AS last_used_at
FROM artist_songs s JOIN artists a ON a.id = s.artist_id
```

**選択の規則**(純関数 `pickReferenceSong(candidates, random)`):

1. **ノイズ除外** — タイトルが `(Live)` / `Remix` / `Instrumental` / `Karaoke` / `Cover` / `Off Vocal` / `Acoustic Version` 等に該当する曲を候補から外す。iTunes の取り込みは 1 アーティスト最大 200 曲で、`fetchSongs()` の重複除去は「正規化した曲名の完全一致」でしか畳まないため、この手の別バージョンはそのまま残っている。**除外した結果 0 件になるなら除外しない**(小さいカタログを空にしない)
2. **アーティストを選ぶ** — 各アーティストの最終使用日時(その人の曲の `last_used_at` の最大)で、未使用 → 古い順にグループを作り、最も古いグループから一様ランダム。**曲一様ではなくアーティスト一様の 2 段階**にするのは、取り込み曲数がアーティストごとに 12〜200 曲と桁違いで、曲一様だと大カタログのアーティストばかり選ばれるため
3. **曲を選ぶ** — そのアーティストの候補曲を同じ規則(未使用 → 最終使用が古い順)でグループ化し、最も古いグループから一様ランダム

この LRU + ランダムなら「直近 N 日は除外」のような設定を増やさずに、①同じ曲の連続を避ける ②候補が少なくても枯渇しない ③候補が増えるほど自然に一巡する、の 3 つを同時に満たす。

**同日 3 曲の重複回避** — 受付(`acceptGeneration`)の時点でタスク行に `artist_song_id` が入るため、2 曲目の選択時には 1 曲目が「使用済み」として見える。結果、その日の 3 曲は(3 組以上登録されていれば)自動的に別アーティスト・別曲になる。

**候補ゼロのフォールバック** — アーティスト未登録、または曲が 1 件も無い場合は現行のプリセット方式(冒険日判定を含む)でそのまま生成する。警告ログを出す。毎日の生成が止まらないことを優先する。

### 2. プロンプト組み立ての分岐を「モード名」から「参照曲の有無」へ(`llm.ts`)

現在 `mode === "artist"` を見ている箇所を、すべて `input.referenceSong` の有無に寄せる(web_search の有効化条件はすでにこの形)。

| 箇所 | 現行 | 変更後 |
|---|---|---|
| リファレンス楽曲+作り方の節 | `mode === "artist" && referenceSong` | `referenceSong` があれば |
| 要素プール+モード指示の節 | daily / daily_adventure で提示 | **参照曲があるときは提示しない**(参照曲が要素を決めるため。提示すると衝突する) |
| 直近の生成スタイル(重複回避) | `mode !== "artist"` のとき注入 | 参照曲が無いときだけ注入 |
| 使用禁止ワードの注記 | `mode === "artist"` は「リファレンス優先」 | 参照曲があれば「リファレンス優先」 |
| 歌声の指示 | `mode === "artist"` は「参照曲の質感に寄せる」 | 同上 |
| `planIssues()` の固有名詞チェック | `mode === "artist" && referenceSong` | `referenceSong` があれば。**daily でも必ず効かせる**(検索結果には固有名詞が大量に入り、Suno は `SENSITIVE_WORD_ERROR` で弾く) |

**今日のコンテキストの節はモード非依存**(`if (input.extraContext)`)なのでコード変更は不要。呼び出し側が渡すだけで参照曲と併存する。ただし**参照曲とニュースが同時に来るのは新しい組み合わせ**なので、作り方の節に優先順位を 1 行足す:

> - 曲調・編成・ボーカルの質感はリファレンス楽曲に寄せ、歌詞のテーマ・情景は今日のコンテキストから採る。両者が衝突する場合は、音はリファレンス・言葉はコンテキストを優先する

### 3. `runDaily` の分割と `POST /api/daily/run` の非同期化(必須)

参照曲ありの生成は実測 192〜255 秒。`POST /api/daily/run` は現在**同期**で、本番のエッジ(Cloudflare 約 100 秒)と iOS 側のタイムアウト(`GenerateView.runDaily()` の 180 秒)のどちらにも掛かる。`POST /api/generate` は 2026-08-09 に非同期化済みだが、`daily/run` は「参照曲が無いため 44 秒のまま」として据え置いてあった。その前提が崩れるので今回あわせて直す。

- `scheduler.ts` の `runDaily()` を受付と本体に割る。案: `startDailyRun(): { task, adventure, complete: () => Promise<db.TaskRow> }`
  - 受付 = 冒険判定(フォールバック時のみ)→ 参照曲の選択 → ニュース取得 → `acceptGeneration()`(参照曲があれば `artist` スナップショット付き)
  - 本体 = `completeGeneration()`
- **スケジューラは `await complete()` のまま**。サーバー内で動き HTTP を経由しないのでタイムアウト制約が無く、順次生成と `last_daily_count` の記録の正しさもこれで保たれる
- **`POST /api/daily/run` は受付直後に 201 を返し**、本体は `void complete().catch(() => {})` で走らせる。失敗は `completeGeneration` が必ずタスクの `FAILED` に記録するので、投げっぱなしでもエラーが進行状況に出る
- **レスポンスのキーの形状は変えない**(`{ task, adventure }`。参照曲ベースでは `adventure` は常に `false`)。旧アプリでもデコードは通る
- ニュース取得(`buildTodayContext()`、数秒)は受付側に置く。受付が数秒かかっても 100 秒の壁には遠く、失敗しても生成は続行する既存の挙動を変えない

クライアント側:

- **iOS `GenerateView.runDaily()`** — `timeout: 180` を外し(既定の 60 秒で足りる)、201 を受けたら `loadTasks()` して進行中カード(「曲を考えています…」)に引き継ぐ
- **管理画面 `app.js`** — 「AI がスタイルと歌詞を考えています…(1〜2 分かかります)」の待機メッセージをやめ、受付後すぐ `refresh()`(`PLANNING` のカードが出る)

`POST /api/daily/run` が `last_daily_date` を更新しない現行仕様は維持する。

### 4. mode と表示

- 参照曲ベースでも **`mode = 'daily'`**。毎日の自動生成であることが第一義で、参照曲は `ref_artist_name` / `ref_song_title` で表現される。管理画面(`app.js` の `if (t.refArtistName)`)も iOS(`APIModels.swift` の `guard let refArtistName`)も**モードで出し分けていない**ので、表示側の改修は不要
- 表示用の `tasks.prompt` は `毎日の自動生成 / <アーティスト>「<曲名>」風` にする(タスク一覧で参照曲が見える)
- 冒険日はフォールバック経路にだけ残る。設定画面の「冒険日確率」に「参照曲の登録が無いときのみ有効」と注記を添える

### 5. `GET /api/generation-params` と生成パラメータ画面

この画面は「おまかせ生成が LLM に注入する入力」を見せる読み取り専用画面で、`runDaily` と同じ関数群から組み立てて**表示と実際の入力がずれないこと**を目的にしている。参照曲ベースになると要素プール・直近スタイル・冒険日確率は注入されなくなるため、そのままだと画面が嘘をつく。

- **API はキーを追加するだけ**(既存キーは残す = 旧アプリ互換):
  - `referenceMode`(参照曲ベースで動いているか = 候補が 1 件以上あるか)
  - `referenceCandidates`(アーティスト名・候補曲数・最終使用日)
  - `recentReferences`(直近に参照した曲 N 件)
- **iOS** — 「参照曲の候補」節を新設し、`referenceMode` が true のときは要素プール節・直近スタイル節・冒険日確率の行を出さない

プリセット機能そのもの(テーブル・管理ページ・評価集計)の撤去は**この作業の範囲外**で、別 TODO「毎日更新が曲参照になったのでそれ以外の機能を洗い出して削除する」で扱う。ここでは「注入されなくなったものを表示しない」までに留める。

### 6. コストと所要時間(運用への影響)

- **1 曲あたり約 $0.36**(入力 12 万トークン・検索 5 回)。`daily_count` が既定の 3 なら **約 $1.1/日 = 月 $33 前後**。従来のプリセット方式は 1 曲約 $0.04 なので約 9 倍。曲数を下げれば線形に下がる
- **1 曲 3〜4.5 分 × 3 曲 = 朝の実行が 10〜14 分**。`tick()` の `ticking` ガードで多重実行はしない。Suno のポーラーは別ループなので、1 曲目の完成待ちと 2 曲目の LLM 生成は並行して進む
- web_search が空振り(無名曲を引いた)ときは警告ログのみで推定に落ちる既存挙動のまま。楽曲詳細の「参照した情報源」が 0 件かどうかで運用中に観測できる

## テスト方針

- `npm run typecheck`
- **隔離 DB のテストサーバー**(`sqlite3 .backup` でコピー・`daily_enabled=false`・ポート 3015)で以下を curl:
  - 選択関数の分布 — scratchpad の使い捨てスクリプトで 1000 回引き、アーティストがほぼ一様に回ること・直近使用の曲が選ばれないこと・ノイズ曲(`(Live)` 等)が出ないこと
  - `POST /admin/api/daily/run` が**即座に 201 + `status: PLANNING`** を返すこと(実測秒数を記録)
  - そのタスクが `mode: daily` かつ `ref_artist_name` / `ref_song_title` / `artist_song_id` を持ち、`PLANNING → PENDING → … → COMPLETE` と遷移すること
  - **通しの実生成 1〜2 曲** — style に検索で確認した BPM・キーが入る / `sources` が 1 件以上付く / style・title・歌詞に固有名詞が無い / 歌詞にニュース由来のテーマが乗っている / `intent` が根拠を書き分けている
  - 3 曲連続で叩いてアーティストが重複しないこと
  - **候補ゼロのフォールバック** — `artist_songs` を空にした隔離 DB で `daily/run` → 現行のプリセット方式(`sources` 0 件・要素プール注入あり)で成立すること
  - LLM 失敗が **タスクの `FAILED` + `error`** に残ること(無効な API キーで再現)
  - `/api/daily/run` のレスポンスキーが `{ task, adventure }` のまま(旧アプリ互換)
- 管理画面をヘッドレス Chrome の CDP 操作で目視(生成ボタン → 進行中カード → 楽曲詳細のリファレンス表示・参照した情報源)
- iOS シミュレータビルド + UI テスト(既存 9 件の回帰なし。生成パラメータ画面の新節を含む)

## Phase 分割

- **Phase 1** — 参照曲の選択(`db.listReferenceCandidates()` + `reference.ts` + 分布確認スクリプト)
- **Phase 2** — プロンプト分岐の一般化(`llm.ts`。参照曲 × ニュースの優先順位、固有名詞チェックの適用拡大)
- **Phase 3** — `runDaily` の分割・`POST /api/daily/run` の非同期化(サーバー + 管理画面 + iOS)
- **Phase 4** — 生成パラメータ(API のキー追加 + iOS の参照曲候補節)
- **Phase 5** — ドキュメント更新(CLAUDE.md / spec 2 本)+ 総合検証(実生成・ヘッドレス目視・UI テスト)+ 後片付け(TODO → DONE、プランのアーカイブ、本番反映を新規 TODO に)

## 非目標(今回はやらない)

- プリセット機能・冒険日・直近スタイル注入など、参照曲ベース化で使われなくなる仕組みの撤去 — 別 TODO
- 👍/👎 の集計による参照曲の重み付け選択(今回は LRU + ランダムのみ)
- 「毎日の対象にする曲」を管理画面・iOS から選ぶフラグ運用
- 参照曲の音源解析による特徴補強

## リスク・観測したいこと

- **深いカット・ライブ版を引く問題** — ノイズ除外と LRU で緩和するが完全ではない。`sources` 0 件が続くようなら、評価による重み付けか対象フラグの導入を検討する
- **`SENSITIVE_WORD_ERROR`** — 参照曲経路では style にコード名(`major7`)を書いてアーティスト名と誤判定された実例が 1 回ある(2026-08-09)。daily に広げると遭遇頻度が上がる可能性がある。頻発するなら `llm.ts` の指示でコード名の書き方を制限する
- **固有名詞の混入** — 検索結果に固有名詞が大量に入る点は手動経路と同じ。`properNounsIn()` + 1 回だけの再生成をそのまま daily にも効かせる
- **朝の実行が 10〜14 分**になるため、失敗時の 30 分後リトライと合わせると 1 日の生成完了が遅れうる。`last_daily_count` による追い生成で最終的には揃う
