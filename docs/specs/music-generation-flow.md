# 音楽生成の流れ

現在の実装が実際にどう動くかを図で説明する文書。設計決定の経緯・理由・データモデルは [music-generation.md](music-generation.md) を参照(この文書は挙動の説明に徹し、決定の記録は持たない)。

対応するコード: `server/src/scheduler.ts`(毎日の自動生成)/ `llm.ts`(LLM 呼び出し)/ `context.ts`(ニュース)/ `generation.ts`(Suno 送信・完了検知)/ `suno/kieai.ts`(プロバイダ実装)。

## 全体像

![全体像: 3 つの入口 → LLM 生成 → Suno → 保存 → iPhone/管理画面、評価のフィードバックループ](music-generation-flow/flow-overview.svg)

入口は複数あるが、どれも同じパイプラインに合流する: **LLM(Claude API)がスタイル・歌詞などの「曲のプラン」を作り、Suno に `customMode: true` で渡す**。生成に使ったプリセットはタスク単位で記録され、完成した曲への評価(👍/👎)はプリセット別の集計として次回生成のプロンプトに注入される。ただし 2026-08-10 に毎日の自動生成が参照曲ベース(要素プールを提示しない)になったため、この評価ループが効くのはカスタム生成と、参照曲の登録が無いときのフォールバックだけになっている。

## 生成の入口

| 入口 | mode | 参照曲 | 評価集計の注入 | 今日のコンテキスト | LLM への指示 |
|---|---|---|---|---|---|
| 毎日の自動生成(スケジューラ) | `daily` | **サーバーが選ぶ** | なし(要素プール自体を提示しない) | あり | 登録済みの曲から 1 曲を選んで「リファレンス楽曲」として提示し、`web_search` で調べさせてから style を書かせる(下の `artist` と同じ指示)。**曲調は参照曲・歌詞のテーマは今日のコンテキスト**から採らせる。1 日の曲数(`daily_count`、既定 3)の分だけ 1 曲ずつ順次生成する |
| ↑ のフォールバック(参照曲の登録が 0 件) | `daily` / `daily_adventure` | なし | あり | あり | プリセット全プールから評価集計を踏まえて選ぶ。通常日は「👍 優先・👎 回避+1 要素だけ普段と違うもの」、冒険日(確率 `adventure_probability`、既定 20%)は「集計に従わなくてよい・大きく外す」 |
| おまかせ生成(管理画面・iOS → `POST /api/daily/run`) | 同上 | 同上 | 同上 | あり | 同上(スケジューラの 1 曲分と同じ手順を実行。ただし `last_daily_date` / `last_daily_count` は更新しないため、当日のスケジュール実行は別途走る) |
| カスタム生成(iOS → `POST /api/generate`) | `manual` | なし | なし(集計で誘導しない) | なし | ユーザーが選んだプリセット+自由テキストを最優先で反映(リアルワードの禁止ワードよりユーザー指定が勝つ) |
| アーティスト経由生成(管理画面・iOS → `POST /api/generate` + `artistSongId`) | `artist` | **ユーザーが選ぶ** | なし(要素プール自体を提示しない) | なし | 登録済みの曲を「リファレンス楽曲」として提示し、**まず `web_search` でその曲の音楽的特徴(BPM・キー・コード進行・楽器編成・ボーカルの音域と質感・プロダクション)を調べさせて**から、英語の音楽用語に翻訳した style を書かせる。固有名詞は禁止(Suno のモデレーション対策)、歌詞は原曲を複製しない完全な新作。参照曲を登録する入口はアーティスト名からと曲名から(逆引き)の 2 つ(下記) |

**プロンプトの組み立ては「モード名」ではなく「参照曲(`referenceSong`)の有無」で分岐する**。参照曲があれば要素プールも直近スタイルも提示せず(参照曲が曲調を決めるため、提示すると再現と衝突する)、無ければ従来どおり提示する。この判定にしてあるおかげで、毎日の自動生成を参照曲ベースへ切り替えたときも `llm.ts` の条件式を寄せるだけで済んだ。使用プリセットの記録と評価の集計反映はどの入口でも共通で働き、リアルワード制限も全入口で注入する。

### 参照曲の選び方(毎日の自動生成、2026-08-10 追加)

サーバーが `server/src/reference.ts` の純関数で選ぶ(LLM には選ばせない)。

1. **ノイズ除外** — 曲名の括弧書き・ダッシュ以降の注釈部分だけを見て `Live` / `Remix` / `Instrumental` / `Karaoke` / `Acoustic Ver` 等の別バージョンを候補から外す(本題側は見ないので「Live and Let Die」は残る)。除外した結果 0 件になるなら除外しない
2. **アーティストを選ぶ** — 各アーティストの最終使用日時(その人の曲の最新 `tasks.created_at`)で「未使用 → 古い順」にグループを作り、最も古いグループから一様ランダム。曲一様ではなくアーティスト一様にするのは、取り込み曲数がアーティストごとに桁違いのため
3. **曲を選ぶ** — そのアーティストの候補曲を同じ規則でグループ化し、最も古いグループから一様ランダム

受付の時点でタスク行に `artist_song_id` が入るため、同じ日の 2 曲目を選ぶときには 1 曲目が「使用済み」として見える。結果その日の 3 曲は自動的に別アーティスト・別曲になり、「直近 N 日は除外」のような設定を持たずに連続回避・枯渇回避・一巡が同時に成立する。候補は `GET /api/generation-params` の `referenceCandidates` として iOS の生成パラメータ画面に「参照曲の候補」節で出る(次に選ばれやすい順)。

### 参照曲(`artist_songs`)の登録経路(2 つ)

アーティスト経由生成は登録済みの曲を参照曲に選ぶ。その曲を登録する入口は 2 つあり、どちらも iTunes Search API(`server/src/itunes.ts`。API キー不要)から取り込む。生成側の処理はどちらも同じ(`POST /api/generate` に `artistSongId` を渡すだけ)。

| 登録経路 | 使う API | 流れ |
|---|---|---|
| アーティスト名から | `GET /api/artists/search` → `POST /api/artists` | 名前で検索 → 候補から選ぶ → そのアーティストの曲(最大 200 曲)を取り込む |
| 曲名から(アーティストは逆引き) | `GET /api/artist-songs/search` → `POST /api/artist-songs` | 曲名で検索 → 候補から選ぶ → 選んだ曲の `artistId` からアーティストを逆引きし、未登録ならアーティストごと登録して曲(最大 200 曲)を取り込む |

曲名検索の候補にはカバー・ピアノ版・オルゴールが多く混ざる(「Lemon」の上位 10 件で本家は 2 行だけ)ため、どちらの経路も**候補一覧から選ばせて**取り違えを防ぐ。曲名検索の track 行の `artistName` は `country=JP` だとローカライズされた表示名(「クイーン」「Official髭男dism」)で返るため、`artists.name` に入れるのは `lookup` の artist 行の正式表記(「Queen」「OFFICIAL HIGE DANDISM」)にする — 詳細は [music-generation.md](music-generation.md) の「曲名からの登録(2026-08-09)」。

`POST /api/artist-songs` の body は `{ itunesTrackId }` だけで、曲メタはサーバーが `lookup` で取り直す(クライアントの申告を信用しない)。アーティストの `lookup` は 200 件で頭打ちのため、選んだ曲がその 200 件に含まれない場合に備えて、対象の曲は必ず個別に `INSERT` する。

## 毎日の自動生成の手順

![毎日の自動生成の 4 手順](music-generation-flow/daily-run-steps.svg)

上図は 1 曲分の手順。スケジューラは 1 日の曲数(`daily_count`、既定 3)の残数分だけこの手順を 1 曲ずつ順次実行し、成功のたびにその日の生成済み数を `settings`(`last_daily_date` / `last_daily_count`)へ記録する。途中で失敗した場合は 30 分後、サーバー停止中に実行時刻を跨いだ場合は起動時のチェックで、いずれも残数だけ追い生成される(重複生成しない)。順次実行のため、2 曲目の参照曲を選ぶときには 1 曲目が使用済みとして見え(結果その日の曲は別アーティストになる)、リアルワードも既存の仕組みでそのまま注入されて曲間の重複を避けられる。冒険日判定はフォールバック経路でのみ 1 曲ごとに行う。

参照曲ありの生成は 1 曲 3〜4.5 分かかるため、既定の 3 曲だと朝の実行は 10〜14 分になる(多重実行は `tick()` の `ticking` ガードで防ぐ。Suno のポーラーは別ループなので 1 曲目の完成待ちと 2 曲目の LLM 生成は並行して進む)。

実行時刻・タイムゾーン・冒険日確率・1 日の曲数・ニュースの ON/OFF は `settings` テーブルで持ち、管理画面の設定ページと iOS の設定タブ(`GET/PUT /api/settings`)から変更できる(次の生成から反映)。冒険日確率だけは**参照曲の登録が無いときのフォールバック経路にしか効かない**(両方の設定画面に注記がある)。思考の深さ(`llm_effort`)も同じ `settings` に入っているが、UI は管理画面のみ。

## LLM 生成の入出力

LLM への入力(user メッセージ)は次のセクションを組み立てて 1 回で渡す。実際に送った全文は `tasks.llm_prompt` に保存され、管理画面の楽曲詳細で確認できる。

使うモデル(`.env` の `LLM_MODEL`、既定 `claude-sonnet-5`)と思考の深さ(`output_config.effort`、既定 `high`)は管理画面の設定ページで確認でき、effort は同ページから 5 段階で切り替えられる(次の生成から反映)。呼び出しはストリーミングで、`max_tokens` は思考と本文の合算で 32,000。

| セクション | 内容 | 提示する条件 |
|---|---|---|
| ユーザーが選んだ要素・自由リクエスト | 選択プリセット+自由テキスト(最優先で反映) | manual のみ |
| リファレンス楽曲+作り方 | 参照曲のアーティスト・曲名・アルバム・リリース年・ジャンルと、**`web_search` で音楽的特徴を調べる指示**(同名異曲を掴まないよう渡したアルバム・リリース年と一致するか確かめる)・英語の音楽用語へ翻訳する指示・固有名詞の禁止・原曲歌詞の複製禁止・`intent` に根拠を項目ごとに書き分ける指示。今日のコンテキストも同時にあるときは「音はリファレンス・言葉はコンテキストを優先する」の 1 行が加わる。自由テキストがあれば「追加の要望」として併記 | **参照曲があるとき**(daily / artist) |
| 利用できる要素プール+モード指示 | プリセット全件(genre・mood・tempo・vocal)にプリセット別の評価集計(👍 N / 👎 N。両方 0 は無印)を併記し、通常日(👍 優先・👎 回避+1 要素は外す)/冒険日(集計に従わなくてよい)の方針を指示 | 参照曲が無い daily / daily_adventure |
| 今日のコンテキスト | ニュース見出し(Google News RSS 米国版・英語の上位 8 件)。「報告ではなく雰囲気・テーマとして織り込む」と指示 | daily / daily_adventure(参照曲の有無を問わない) |
| 直近の生成スタイル | 直近 10 曲の style(重複回避用。1 日 3 曲でも数日分を見渡せる件数) | **参照曲が無いとき**(曲の重複は参照曲の選択側 LRU が担うため) |
| 使用禁止ワード/残り 1 回のワード | リアルワードの使用回数集計から算出(下記)。参照曲があればリファレンスの再現、無ければ manual のユーザー指定が優先と注記 | 全モード |
| 出力条件 | インストゥルメンタル指定、歌声の特徴を style に必ず含める指示(参照曲があれば「参照曲のボーカルの質感に寄せる」に差し替え) | 全モード |

出力は構造化出力(JSON Schema)で受け取る:

| フィールド | 内容 |
|---|---|
| `style` / `styleJa` | Suno に渡す英語スタイルプロンプト(500 文字以内)とその日本語訳 |
| `title` | 曲のタイトル(英語) |
| `lyrics` / `lyricsJa` | セクションタグ付きの英語歌詞と日本語訳(インストは空文字列) |
| `intent` | この曲の狙い(日本語 2〜3 文。管理画面・iOS の楽曲詳細に表示) |
| `realWorldWords` | 曲の中心となった語(英語小文字 5〜8 個)。保存して使用回数制限に使う |
| `sources` | `web_search` で参照した情報源の URL / タイトル(検索しない入口では空配列)。`tasks.llm_sources` に JSON で保存し、管理画面・iOS の楽曲詳細に「参照した情報源」として表示 |
| `usedPresets` | 採用したプリセット(`{category, value}` の配列。提示値を一字一句写す指示)。サーバーで `presets` と照合して `task_presets` に保存し(不一致は警告ログのみ)、manual はユーザー選択との和集合を記録。評価集計の元になり、楽曲詳細の「使用プリセット」に表示 |

### リアルワードの使用制限と検証リトライ

似たテーマの連続生成を防ぐ仕組み(詳細な決定は [music-generation.md](music-generation.md) の「リアルワードの使用制限」)。生成前に直近ウィンドウ(既定 30 日)の使用回数を集計し、上限(既定 2 回)に達した語を「使用禁止ワード」としてプロンプトに注入する。出力の `realWorldWords` に禁止ワードが残っていたら**指示を強めて 1 回だけ再生成**し、それでも残る場合は警告ログのみで採用する(生成は止めない)。

**参照曲があるとき**(daily / artist)はこれに加えて**固有名詞の混入**(style / title / lyrics のアーティスト名、title の曲名)も検査し、同じ 1 回の再生成にまとめて指示する。Suno は固有名詞をモデレーションで弾く(`SENSITIVE_WORD_ERROR` → タスク FAILED)ため、送信前に落としておく必要がある。検索結果には固有名詞が大量に入るので、この検査はモード名ではなく参照曲の有無で掛ける(モード名で見ると daily の曲だけ素通りしてしまう)。

## 生成の受付と非同期実行

参照曲ありの生成は `web_search` で調べるため 1 曲あたり 3 分ほどかかる。本番のエッジ(Cloudflare)は約 100 秒でプロキシがタイムアウトするため、`POST /api/generate` と `POST /api/daily/run` は**受付だけ済ませて即座に返す**。

1. **受付**(`acceptGeneration`)— LLM を呼ぶ前に `status = 'PLANNING'` のタスク行を作り、201 で返す(実測 0.005 秒)。この時点では `provider_task_id` は空
2. **本体**(`completeGeneration`、バックグラウンド)— LLM 生成 → プランをタスクに書き込み → Suno へ送信 → `provider_task_id` を埋めて `PENDING` に進める
3. 失敗したら必ずタスクを `FAILED` にしてから再送出する。投げっぱなしの呼び出しでもエラーが `tasks.error` に残り、進行状況の画面で観測できる

`PLANNING` はポーラーの対象外(`provider_task_id` が空のため)。サーバー再起動時に `PLANNING` のまま残っているタスクは、LLM 呼び出しを再開できないので起動時に `FAILED` にする。

毎日の自動生成も同じ形で、`scheduler.ts` の `startDailyRun()` が受付(参照曲の選択 → ニュース取得 → `acceptGeneration()`)を行い `complete()` を返す。**スケジューラはサーバー内で動くので `await complete()` のまま**(HTTP を経由せずタイムアウト制約が無く、順次生成と `last_daily_count` の記録の正しさもこれで保たれる)、**`POST /api/daily/run` は受付直後に 201 を返して本体を投げっぱなしにする**(実測 0.03〜0.19 秒)。応答のキーは `{ task, adventure }` のままなので旧アプリでもデコードは通る。

## Suno タスクの状態遷移

LLM のプランは `customMode: true`(style / prompt=歌詞 / title / model)で Suno(kie.ai)へ送信され、`tasks` に記録される。以降は 10 秒間隔のポーラーが進行を追う(下図は Suno 送信後。その手前に上記の `PLANNING` が入る)。

![タスクの状態遷移: PENDING → TEXT_SUCCESS → FIRST_SUCCESS → SUCCESS → COMPLETE、失敗時 FAILED](music-generation-flow/task-status.svg)

- `SUCCESS` を検知したら**すぐ**音源・カバー画像を `data/` へダウンロードする(プロバイダの URL は一時ファイル置き場のため)。保存が終わると `COMPLETE` になり `tracks` に登録される
- `CALLBACK_EXCEPTION` は曲データがあれば成功扱い、無ければ失敗扱い(完了検知はポーリングで行い、コールバックは使っていない)
- 進行状況は `GET /api/tasks` で取れ、iOS のライブラリ上部カード・生成タブと管理画面が 5 秒ポーリングで表示する

## 評価のフィードバックループ

**2026-08-10 以降、このループが効くのはカスタム生成(`manual`)と、参照曲の登録が無いときのフォールバックだけ**(毎日の自動生成は参照曲ベースになり要素プールを提示しなくなった)。プリセット機能そのものの整理は別途行う。

iPhone・管理画面で付けた 👍/👎 は `tracks.rating` に保存され、次回生成のたびに `task_presets`(その曲の生成に使ったプリセットの記録)と join してプリセット別の 👍/👎 を全期間集計し、要素プールの行に併記して注入する(👍 の多い要素を優先・👎 の多い要素は回避と指示)。集計は保存値を持たないステートレス方式なので、評価の変更・解除が次の生成に即反映される。冒険日の曲も評価対象で、👍 が付けばその要素の集計が上がり以後の通常日に選ばれやすくなる(冒険日自体は集計に従わなくてよいと指示)。プリセット別の集計は presets 管理ページの各行と `GET /api/presets`(`upCount` / `downCount`)で確認できる。
