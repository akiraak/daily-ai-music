# 音楽生成の流れ

現在の実装が実際にどう動くかを図で説明する文書。設計決定の経緯・理由・データモデルは [music-generation.md](music-generation.md) を参照(この文書は挙動の説明に徹し、決定の記録は持たない)。

対応するコード: `server/src/scheduler.ts`(毎日の自動生成)/ `llm.ts`(LLM 呼び出し)/ `context.ts`(ニュース)/ `generation.ts`(Suno 送信・完了検知)/ `suno/kieai.ts`(プロバイダ実装)。

## 全体像

![全体像: 3 つの入口 → 参照曲 → LLM 生成(web_search)→ Suno → 保存 → iPhone/管理画面](music-generation-flow/flow-overview.svg)

入口(トリガ)は 3 つあるが、どれも同じパイプラインに合流する: **登録済みの曲(`artist_songs`)から選んだ 1 曲を「リファレンス楽曲」として LLM(Claude API)に渡し、`web_search` でその曲の音楽的特徴を調べさせてスタイル・歌詞などの「曲のプラン」を作らせ、Suno に `customMode: true` で渡す**。生成モードは `daily` と `artist` の 2 つで、違いは参照曲を誰が選ぶか(サーバー / ユーザー)とニュースを注入するかだけ。プロンプトの組み立ては共通。

## 生成の入口

| 入口 | mode | 参照曲 | 今日のコンテキスト | 追加の要望 |
|---|---|---|---|---|
| 毎日の自動生成(スケジューラ) | `daily` | **サーバーが選ぶ**(下記の LRU) | あり | なし |
| おまかせ生成(管理画面・iOS → `POST /api/daily/run`) | `daily` | 同上 | あり | なし |
| アーティスト経由生成(管理画面・iOS → `POST /api/generate` + `artistSongId`) | `artist` | **ユーザーが選ぶ** | なし | 管理画面の「追加の要望」欄(任意)|

- 毎日の自動生成は 1 日の曲数(`daily_count`、既定 3)の分だけ 1 曲ずつ順次生成する。おまかせ生成はその 1 曲分と同じ手順を実行するが、`last_daily_date` / `last_daily_count` は更新しないため当日のスケジュール実行は別途走る
- **参照曲の候補が 0 件なら生成しない**(アーティスト未登録)。スケジューラはエラーとして扱い 30 分後に再試行、`POST /api/daily/run` は 409 を返す。`last_daily_*` を進めないので、アーティストを登録すればその日のうちに追い生成される
- LLM への指示は共通 — 参照曲を「リファレンス楽曲」として提示し、**まず `web_search` でその曲の音楽的特徴(BPM・キー・コード進行・楽器編成・ボーカルの音域と質感・プロダクション)を調べさせて**から、英語の音楽用語に翻訳した style を書かせる。固有名詞は禁止(Suno のモデレーション対策)、歌詞は原曲を複製しない完全な新作。今日のコンテキストが同時にあるときは「**曲調は参照曲・歌詞のテーマはコンテキスト**」の優先順位を添える
- **歌詞は設定した言語で書かせる**(設定 `vocal_language`、既定 `ja`。2026-08-11 追加。それ以前は英語固定 + 日本語訳)。生成のたびに設定を読むので、変更は次の生成に効く
- 参照曲を登録する入口はアーティスト名からと曲名から(逆引き)の 2 つ(下記)
- リアルワード制限は両入口で注入する

かつては 3 つ目の入口としてカスタム生成(`mode = 'manual'`、プリセット+自由テキスト)があり、プロンプトは「モード名」ではなく「参照曲(`referenceSong`)の有無」で分岐して、参照曲が無いときは要素プール(評価集計付き)と直近スタイルを提示していた。2026-08-10 に参照曲ベースへ統一し、分岐ごと削除した(経緯: [music-generation.md](music-generation.md) の「参照曲ベース化で使われなくなった機能の削除」)。

### 参照曲の選び方(毎日の自動生成、2026-08-10 追加)

サーバーが `server/src/reference.ts` の純関数で選ぶ(LLM には選ばせない)。

1. **ノイズ除外** — 曲名の括弧書き・ダッシュ以降の注釈部分だけを見て `Live` / `Remix` / `Instrumental` / `Karaoke` / `Acoustic Ver` 等の別バージョンを候補から外す(本題側は見ないので「Live and Let Die」は残る)。除外した結果 0 件になるなら除外しない
2. **アーティストを選ぶ** — 各アーティストの最終使用日時(その人の曲の最新 `tasks.created_at`)で「未使用 → 古い順」にグループを作り、最も古いグループから一様ランダム。曲一様ではなくアーティスト一様にするのは、取り込み曲数がアーティストごとに桁違いのため
3. **曲を選ぶ** — そのアーティストの候補曲を同じ規則でグループ化し、最も古いグループから一様ランダム

受付の時点でタスク行に `artist_song_id` が入るため、同じ日の 2 曲目を選ぶときには 1 曲目が「使用済み」として見える。結果その日の 3 曲は自動的に別アーティスト・別曲になり、「直近 N 日は除外」のような設定を持たずに連続回避・枯渇回避・一巡が同時に成立する。候補は `GET /api/generation-params` の `referenceCandidates` として iOS の生成パラメータ画面に「参照曲の候補」節で出る(次に選ばれやすい順)。

### 参照曲(`artist_songs`)の登録経路(2 つ)

アーティスト経由生成は登録済みの曲を参照曲に選ぶ。その曲を登録する入口は 2 つあり、どちらも iTunes Search API(`server/src/itunes.ts`。API キー不要)から取り込む。生成側の処理はどちらも同じ(`POST /api/generate` に `artistSongId` を渡すだけ)。

| 登録経路 | 使う API | 流れ |
|---|---|---|
| アーティスト名から | `GET /api/artists/search` → `POST /api/artists` | 名前で検索 → 候補から選ぶ → そのアーティストの曲(最大 200 曲)を取り込む |
| 曲名から(アーティストは逆引き) | `GET /api/artist-songs/search` → `POST /api/artist-songs` | 曲名で検索 → 候補から選ぶ → 選んだ曲の `artistId` からアーティストを逆引きし、未登録ならアーティストごと登録して曲(最大 200 曲)を取り込む |

曲名検索の候補にはカバー・ピアノ版・オルゴールが多く混ざる(「Lemon」の上位 10 件で本家は 2 行だけ)ため、どちらの経路も**候補一覧から選ばせて**取り違えを防ぐ。曲名検索の track 行の `artistName` は `country=JP` だとローカライズされた表示名(「クイーン」「Official髭男dism」)で返るため、`artists.name` に入れるのは `lookup` の artist 行の正式表記(「Queen」「OFFICIAL HIGE DANDISM」)にする — 詳細は [music-generation.md](music-generation.md) の「曲名からの登録(2026-08-09)」。

`POST /api/artist-songs` の body は `{ itunesTrackId }` だけで、曲メタはサーバーが `lookup` で取り直す(クライアントの申告を信用しない)。アーティストの `lookup` は 200 件で頭打ちのため、選んだ曲がその 200 件に含まれない場合に備えて、対象の曲は必ず個別に `INSERT` する。

## 毎日の自動生成の手順

![毎日の自動生成の 4 手順](music-generation-flow/daily-run-steps.svg)

上図は 1 曲分の手順。スケジューラは 1 日の曲数(`daily_count`、既定 3)の残数分だけこの手順を 1 曲ずつ順次実行し、成功のたびにその日の生成済み数を `settings`(`last_daily_date` / `last_daily_count`)へ記録する。途中で失敗した場合(参照曲が 0 件のときもここに含まれる)は 30 分後、サーバー停止中に実行時刻を跨いだ場合は起動時のチェックで、いずれも残数だけ追い生成される(重複生成しない)。順次実行のため、2 曲目の参照曲を選ぶときには 1 曲目が使用済みとして見え(結果その日の曲は別アーティストになる)、リアルワードも既存の仕組みでそのまま注入されて曲間の重複を避けられる。

参照曲ありの生成は 1 曲 3〜4.5 分かかるため、既定の 3 曲だと朝の実行は 10〜14 分になる(多重実行は `tick()` の `ticking` ガードで防ぐ。Suno のポーラーは別ループなので 1 曲目の完成待ちと 2 曲目の LLM 生成は並行して進む)。

実行時刻・タイムゾーン・1 日の曲数・ニュースの ON/OFF は `settings` テーブルで持ち、管理画面の設定ページと iOS の設定タブ(`GET/PUT /api/settings`)から変更できる(次の生成から反映)。思考の深さ(`llm_effort`)も同じ `settings` に入っているが、UI は管理画面のみ。

## LLM 生成の入出力

LLM への入力(user メッセージ)は次のセクションを組み立てて 1 回で渡す。実際に送った全文は `tasks.llm_prompt` に保存され、管理画面の楽曲詳細で確認できる。

使うモデル(`.env` の `LLM_MODEL`、既定 `claude-sonnet-5`)と思考の深さ(`output_config.effort`、既定 `high`)は管理画面の設定ページで確認でき、effort は同ページから 5 段階で切り替えられる(次の生成から反映)。呼び出しはストリーミングで、`max_tokens` は思考と本文の合算で 32,000。

**2026-08-10 以降、プロンプトは分岐の無い直線**(参照曲が必ずあるため)。セクションは上から順に:

| セクション | 内容 | 提示する条件 |
|---|---|---|
| リファレンス楽曲 | 参照曲のアーティスト・曲名・アルバム・リリース年・ジャンル | 常時 |
| 作り方(厳守) | **`web_search` で音楽的特徴を調べる指示**(同名異曲を掴まないよう渡したアルバム・リリース年と一致するか確かめる)・英語の音楽用語へ翻訳する指示・固有名詞の禁止・原曲歌詞の複製禁止・`intent` に根拠を項目ごとに書き分ける指示・`sources` に情報源を列挙する指示。今日のコンテキストも同時にあるときは「音はリファレンス・言葉はコンテキストを優先する」の 1 行が加わる | 常時 |
| 追加の要望 | リファレンスに重ねて反映する自由テキスト | `artist` で入力があるとき(管理画面の「追加の要望」欄) |
| 今日のコンテキスト | ニュース見出し(Google News RSS 米国版・英語の上位 8 件)。「報告ではなく雰囲気・テーマとして織り込む」と指示 | `daily`(ニュース設定 ON かつ取得成功時) |
| 使用禁止ワード/残り 1 回のワード | リアルワードの使用回数集計から算出(下記)。リファレンスの再現と衝突する場合はリファレンス優先と注記 | 該当する語があるとき |
| 出力条件 | インストゥルメンタル指定、**歌詞の言語**(設定 `vocal_language`。2026-08-11 追加)、歌声の特徴(性別・声質・年齢感)を style に必ず含め参照曲のボーカルの質感に寄せる指示。日本語のときは表記ルール(漢字かな交じり・算用数字を使わない・誤読しやすい語を避ける・助詞を「ワ」「エ」と書くような崩しはしない)と、style に日本語ボーカル指定を含める指示が加わる | 常時 |

出力は構造化出力(JSON Schema)で受け取る:

| フィールド | 内容 |
|---|---|
| `style` / `styleJa` | Suno に渡す英語スタイルプロンプト(500 文字以内)とその日本語訳 |
| `title` | 曲のタイトル(歌詞の言語に寄せる。日本語のときも英語タイトルが自然ならそれでよい) |
| `lyrics` / `lyricsJa` | `lyrics` = **Suno に渡す原詞**(歌声の言語。セクションタグは英語のまま)、`lyricsJa` = その日本語訳。**原詞が日本語のときは `lyricsJa` をスキーマから外す**(訳が要らないため、項目ごと出力させない)。インストは空文字列 |
| `intent` | この曲の狙い(日本語 2〜3 文。管理画面・iOS の楽曲詳細に表示) |
| `realWorldWords` | 曲の中心となった語(英語小文字 5〜8 個)。保存して使用回数制限に使う |
| `sources` | `web_search` で参照した情報源の URL / タイトル(検索できなかったときは空配列)。`tasks.llm_sources` に JSON で保存し、管理画面・iOS の楽曲詳細に「参照した情報源」として表示 |

### リアルワードの使用制限と検証リトライ

似たテーマの連続生成を防ぐ仕組み(詳細な決定は [music-generation.md](music-generation.md) の「リアルワードの使用制限」)。生成前に直近ウィンドウ(既定 30 日)の使用回数を集計し、上限(既定 2 回)に達した語を「使用禁止ワード」としてプロンプトに注入する。出力の `realWorldWords` に禁止ワードが残っていたら**指示を強めて 1 回だけ再生成**し、それでも残る場合は警告ログのみで採用する(生成は止めない)。

これに加えて**固有名詞の混入**(style / title / lyrics のアーティスト名、title の曲名)も毎回検査し、同じ 1 回の再生成にまとめて指示する。Suno は固有名詞をモデレーションで弾く(`SENSITIVE_WORD_ERROR` → タスク FAILED)ため、送信前に落としておく必要がある。検索結果には固有名詞が大量に入るのでこの検査は必須で、参照曲が必ずある現在は無条件に掛かる。

## 生成の受付と非同期実行

参照曲ありの生成は `web_search` で調べるため 1 曲あたり 3 分ほどかかる。本番のエッジ(Cloudflare)は約 100 秒でプロキシがタイムアウトするため、`POST /api/generate` と `POST /api/daily/run` は**受付だけ済ませて即座に返す**。

1. **受付**(`acceptGeneration`)— LLM を呼ぶ前に `status = 'PLANNING'` のタスク行を作り、201 で返す(実測 0.005 秒)。この時点では `provider_task_id` は空
2. **本体**(`completeGeneration`、バックグラウンド)— LLM 生成 → プランをタスクに書き込み → Suno へ送信 → `provider_task_id` を埋めて `PENDING` に進める
3. 失敗したら必ずタスクを `FAILED` にしてから再送出する。投げっぱなしの呼び出しでもエラーが `tasks.error` に残り、進行状況の画面で観測できる

`PLANNING` はポーラーの対象外(`provider_task_id` が空のため)。サーバー再起動時に `PLANNING` のまま残っているタスクは、LLM 呼び出しを再開できないので起動時に `FAILED` にする。

毎日の自動生成も同じ形で、`scheduler.ts` の `startDailyRun()` が受付(参照曲の選択 → ニュース取得 → `acceptGeneration()`)を行い `complete()` を返す。**スケジューラはサーバー内で動くので `await complete()` のまま**(HTTP を経由せずタイムアウト制約が無く、順次生成と `last_daily_count` の記録の正しさもこれで保たれる)、**`POST /api/daily/run` は受付直後に 201 を返して本体を投げっぱなしにする**(実測 0.03〜0.19 秒)。応答は `{ task }`。参照曲の候補が 0 件のときは受付の段階で `NoReferenceSongError` になり、409 が返る(タスク行は作られない)。

## Suno タスクの状態遷移

LLM のプランは `customMode: true`(style / prompt=歌詞 / title / model)で Suno(kie.ai)へ送信され、`tasks` に記録される。以降は 10 秒間隔のポーラーが進行を追う(下図は Suno 送信後。その手前に上記の `PLANNING` が入る)。

![タスクの状態遷移: PENDING → TEXT_SUCCESS → FIRST_SUCCESS → SUCCESS → COMPLETE、失敗時 FAILED](music-generation-flow/task-status.svg)

- `SUCCESS` を検知したら**すぐ**音源・カバー画像を `data/` へダウンロードする(プロバイダの URL は一時ファイル置き場のため)。保存が終わると `COMPLETE` になり `tracks` に登録される
- `CALLBACK_EXCEPTION` は曲データがあれば成功扱い、無ければ失敗扱い(完了検知はポーリングで行い、コールバックは使っていない)
- 進行状況は `GET /api/tasks` で取れ、iOS のライブラリ上部カード・生成タブと管理画面が 5 秒ポーリングで表示する
