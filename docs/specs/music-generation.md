# 音楽生成の仕組み(2026-08-06 決定)

会話で詰めた設計決定。実装プランは [docs/plans/music-generation-engine.md](../plans/music-generation-engine.md)。
**現在の実装の流れの図解は [music-generation-flow.md](music-generation-flow.md)**(この文書は決定の記録、あちらは挙動の説明)。

## 全体像

**現在(2026-08-10 以降)**: 登録済みの曲(`artist_songs`)から選んだ 1 曲を「リファレンス楽曲」として LLM(Claude API)に渡し、`web_search` でその曲の音楽的特徴を調べさせてからスタイルプロンプト+英語歌詞+日本語訳を書かせ、Suno に `customMode: true` で渡す。生成経路は `daily`(サーバーが参照曲を選ぶ)と `artist`(ユーザーが選ぶ)の 2 つで、どちらも必ず参照曲を持つ。

```
参照曲(artist_songs から LRU で選択)─→ LLM(Sonnet 5 + web_search)
今日のコンテキスト(ニュース) ────→   ──→ スタイル + 英語歌詞 + 日本語訳 + タイトル + 参照した情報源
リアルワード制限(直近 30 日) ────→                │
                                     customMode: true で Suno へ
                                                 │
                                   2 曲完成 → 1 曲目のみ data/ へ保存
```

**経緯**: 当初は LLM がプリセット(要素プール)をもとに毎回組み立て、生成に使ったプリセットをタスク単位で記録して、ユーザーの評価(👍/👎)をプリセット別の集計として次回生成のプロンプトに注入する方式だった(2026-08-08 変更: 当初の「好みプロファイル」文書方式を廃止し、評価の反映を使用プリセット×評価集計に一本化)。2026-08-10 に毎日の自動生成を参照曲ベースへ切り替えた結果この学習ループが経路から外れ、**同日中にプリセット・評価・冒険日・カスタム生成をすべて削除した**(下記「参照曲ベース化で使われなくなった機能の削除」)。

## 生成フロー(毎日の自動生成)

1. スケジューラが PT 6:00 を検知(停止中に跨いだら起動時に追い生成)。2026-08-09 変更: 1 日の曲数 `daily_count`(既定 3)の残数分だけ以下 2〜6 を 1 曲ずつ順次実行する。順次のため 2 曲目以降のプロンプトには同日の前の曲のスタイル・リアルワードが既存の仕組みで注入され、曲間の重複を避けられる(直近スタイルの注入は 5 → 10 件に拡大)
2. **参照曲の選択(2026-08-10 追加)**: 登録済みの曲(`artist_songs`)から 1 曲を選ぶ。選ぶのはサーバー(LLM には選ばせない)。0 件なら生成せずエラーにする(同日中の変更。当初はプリセット方式へフォールバックし、そこでだけ確率 20% の冒険日判定が働いていた)
3. **外部コンテキスト取得(2026-08-07 追加)**: ニュース(Google News RSS 日本版)を取得し「今日のコンテキスト」としてプロンプトに注入。取得失敗やソース OFF(設定画面で切替)ならセクション無しで続行し、生成は止めない。注入は毎日の自動生成のみ(手動リクエストは対象外)。天気(Open-Meteo)も併せて注入していたが 2026-08-09 に削除(生成への寄与が薄いため。コンテキストはニュースに一本化)。2026-08-09 変更: ニュースのソースを Google News RSS 日本版から米国版(英語)へ切り替え — 歌詞は英語で生成するため、海外英語メディアの見出しの方がテーマ語(リアルワード)や雰囲気が英語歌詞に自然に馴染む。XML 構造は同一のためパーサ・件数上限(8 件)・失敗時スキップは不変更。2026-08-11: 歌詞の既定が日本語になったが、**ソースは米国版(英語)のまま据え置いた** — LLM は英語の見出しからテーマを汲んで日本語歌詞に落とせる(実生成で確認済み)。日本版に戻すかは実運用を見てから判断する
4. **LLM コール(生成)**: 入力 = 参照曲(リファレンス楽曲+`web_search` で調べる指示)+ 今日のコンテキスト + リアルワードの使用制限。出力(JSON) = スタイルプロンプト(英語)/タイトル/英語歌詞/日本語訳/狙いの説明(日本語、管理画面表示用)/リアルワード(曲の中心となった語、英語小文字 5〜8 個)/参照した情報源(2026-08-09 追加)。旧: 参照曲が無いときはプリセット全プール(👍/👎 集計を併記)+ 直近スタイル + モード(通常/冒険)を入力にし、出力に使用プリセットも含めていた(2026-08-10 廃止)
5. Suno へ `customMode: true`(style / prompt=歌詞 / title / model)で送信
6. 完了検知〜音源保存は既存フローのまま。生成された 2 曲のうち 1 曲目のみ採用・保存する(2026-08-07 変更)。歌詞・訳・スタイル・狙いはタスク単位で保存

かつては生成の前に **LLM コール(プロファイル更新)** があったが 2026-08-08 に廃止(評価の反映をプリセット集計に一本化し、毎朝の LLM コールが 1 回減った)。

### リアルワードの使用制限(2026-08-07 追加)

似たテーマの曲の連続生成を防ぐ仕組み。全モード(現在は daily / artist)共通で `generateSongPlan` が一元処理する。

- 生成のたびに LLM が出力した `realWorldWords` を `real_world_words` テーブルへ保存(小文字正規化)
- 生成前に直近ウィンドウ(既定 30 日、`word_window_days`)の使用回数を集計し、上限(既定 2 回、`word_max_uses`)に達した語は「使用禁止ワード」、残り 1 回の語は「残り 1 回のワード」としてプロンプトに注入。ウィンドウを外れた語は自動的に再利用可能になる(物理削除なし)
- 禁止ワードよりリファレンス楽曲の再現が優先されると明記して注入する(2026-08-10 まではこの注記が manual のユーザー指定優先と出し分けだった)
- **検証リトライ**: 出力の realWorldWords に禁止ワードが残っていたら指示を強めて 1 回だけ再生成。それでも残る場合は警告ログのみで採用(生成を止めない)
- 使用状況は iOS の生成パラメータ画面で確認できる(2026-08-10 まで管理画面のパラメータ一覧ページにもリアルワード表があった)

### ~~手動リクエスト~~(2026-08-10 廃止)

プリセットを選択(+自由テキスト)→ 同じ LLM 生成 → 同じ Suno フロー、という 3 つ目の入口があった(`mode = 'manual'`)。手動生成の曲への評価も同じプリセット集計に反映され(使用プリセットはユーザー選択と LLM 出力の照合結果の和集合を記録)、ただし manual の生成プロンプトには評価集計を注入しなかった — ユーザー指定が最優先で、集計で誘導しないため(2026-08-08)。プリセットを送るクライアントが最終的に 1 つも無くなったため 2026-08-10 に廃止した。

### アーティスト経由生成(2026-08-09 追加)

好きなアーティストの特定の曲を「リファレンス楽曲」として選び、それに似た新曲を作る 3 つ目の生成経路(`mode = 'artist'`)。アーティストを登録すると iTunes からその人の曲が取り込まれ、曲を選んで生成する。

| 項目 | 決定 |
|---|---|
| 楽曲データソース | **iTunes Search API**。API キー不要・無料で `.env` にも本番のシークレット管理にも影響が出ない(Spotify はキー必須、MusicBrainz は 1 req/s 制限+曲の網羅性が中途半端)。日本語で検索してもヒットするが返る名前はローマ字表記のことが多く(「米津玄師」→「Kenshi Yonezu」)別名義も混ざるため、**候補一覧から選ばせて取り違えを防ぐ**。`lookup` の `limit` は 200 で頭打ち。同名の重複(シングル版・アルバム版・ベスト盤)が 2 割前後あるため曲名の正規化(trim + 小文字化)で最古のリリースを残す。track 行の `artistId` が登録アーティストと一致しないコラボ曲も本人の曲なので除外しない |
| Suno への渡し方 | **固有名詞は Suno に渡さない**。Suno はプロンプト内のアーティスト名・曲名をモデレーションで弾く(`kieai.ts` の `FAILURE_STATUSES` にある `SENSITIVE_WORD_ERROR`)。そのためこの経路の肝は「参照曲を名指しで伝える」ことではなく、**LLM に参照曲の音楽的特徴(ジャンル・テンポ・リズム・コード進行の雰囲気・楽器編成・ボーカルの質感・プロダクション)を具体的な英語の音楽用語へ翻訳させ、固有名詞を落とした style を書かせる**こと。送信前にサーバー側で混入を検査する(下記) |
| 混入の検査 | style / title / lyrics にアーティスト名、title に曲名が含まれていないかを検査(小文字化。ASCII 名は語境界で見て「Air」が「airplane」に誤ヒットしないようにし、3 文字未満の名前は誤検出が多いので見ない)。曲名は普通の単語のこと(「Lemon」等)があるため歌詞は見ない。違反時は禁止ワードと同じく指示を強めて**1 回だけ再生成**し、それでも残れば警告ログのみで続行(Suno 側で弾かれれば FAILED として観測できる) |
| 歌詞 | 原曲の複製・翻訳・言い換えを明示的に禁止し、テーマ・情景の参考に留めた完全な新作にする(著作権上の配慮) |
| LLM が曲を知らない場合 | そのアーティストの一般的な作風から推定してよいと指示し、**何を根拠にしたか(曲を知っている / 作風からの推定)を `intent` に書かせる**。結果の妥当性をユーザーが判断できるようにするため |
| 既存の学習ループとの関係 | 要素プールを LLM に提示しない(`usedPresets` は空)ので、この経路の 👍/👎 はプリセット集計を汚さない。直近スタイルの重複回避は「参照曲に似せる」目的と矛盾するので注入しない。リアルワード制限は注入するが、参照曲の再現と衝突する場合はリファレンスを優先すると明記する。歌声も「幅広い声色を試す」ではなく「参照曲のボーカルの質感に寄せる」に差し替える(2026-08-10 に学習ループ側 — プリセット・評価・直近スタイル — がすべて廃止され、ここに書いた「提示しない」が唯一の挙動になった) |
| 非目標(今回はやらない) | ~~毎日の自動生成への織り込み~~(2026-08-10 に実施。下記「毎日の自動生成を参照曲ベースに変更」)/ アーティスト別・曲別の評価集計と学習への反映(`tasks.artist_id` は記録だけ先に用意)/ ~~Web 検索~~(2026-08-09 に導入。下記)・音源解析による参照曲の特徴補強 |

#### web_search による参照曲の調査(2026-08-09 追加)

参照曲について LLM に渡していたのは iTunes から取った 5 項目(アーティスト・曲名・アルバム・リリース年・ジャンル)だけで、曲を知らなければ作風から推定させていた。**問題は「知らない」ことではなく「知っているつもりで外す」こと** — 同じ参照曲(OFFICIAL HIGE DANDISM「Pretender」)で、検索なしの生成は `138 BPM shuffle groove` と書いたうえで intent に「この曲を知っている前提で踏襲した」と申告した。実際は約 92 BPM で、ユーザーが intent を読んでも誤りに気づけない。Claude API の `web_search` サーバーツールで実際に調べさせる方式に切り替えた。

| 項目 | 決定 |
|---|---|
| 検索を有効にする条件 | **`referenceSong` の有無**(モード名では判定しない)。調べる対象があるのは実在の曲を指定されたときだけで、daily はニュース文脈が、manual はユーザーの自由記述が入力なので検索先が無い。この判定にしておくと、毎日の自動生成が曲指定になったときも自動的に検索が効く |
| ツールのバージョン | `web_search_20260209`(動的フィルタリング付き)。応答に `code_execution_tool_result` が混ざるが、これは動的フィルタリングが内部で使うもので、**`code_execution` を別途宣言してはいけない**(実行環境が 2 つになりモデルが混乱する) |
| 構造化出力との併用 | **できる**(実測)。`output_config.format`(json_schema)と server tool を同時に指定して `stop_reason: end_turn`、JSON パースも成功する。`firstText()` は `content.find(b => b.type === "text")` なので server tool のブロックが混ざっても壊れない |
| 検索の上限 | `max_uses: 5`。実測ではこれで BPM・キー・コード進行・ボーカルの音域まで揃った。増やすと精度より先に時間とコストが伸びる |
| `pause_turn` | server tool がサーバー側の反復上限に達すると返る。同じ user メッセージ + 直前の assistant 応答を送り直して再開する(「続けて」等の追加メッセージは付けない)。実測では出なかったが `max_uses` 次第で起こるため実装してある |
| 検索の失敗 | **例外にならない**。HTTP 200 で `web_search_tool_result.content` がエラーオブジェクト(配列ではない)で返る。検索できなくても作風からの推定で書けるので**警告ログのみで続行**する |
| 同名異曲への対処 | プロンプトで「渡したアーティスト名・アルバム・リリース年と一致する曲かを必ず確かめる」と指示する。実測では Tunebat / ufret / Shazam / Wikipedia いずれも正しい曲を引いた |
| 固有名詞の混入 | 検索結果には固有名詞が大量に入るため、リスクは上がる。既存の `properNounsIn()` 検査と 1 回だけの再生成を**そのまま維持**する(実測 2 回では混入しなかったが n=2 では判断できないので運用で観測する) |
| 出典の記録 | `SONG_PLAN_SCHEMA` に `sources`(参照した URL / タイトル)を追加し `tasks.llm_sources` に JSON で保存、楽曲詳細に表示する。intent には根拠を**項目ごとに書き分け**させる(検索で確認した / 曲を知っている / 作風からの推定) |
| コストとレイテンシ | 実測で 1 曲あたり **192 秒 / 入力 123,899・出力 11,086 トークン / 検索 5 回**(検索なしは 44 秒・入力約 700 トークン)。1 曲約 $0.36 で従来の約 9 倍。手動トリガの参照曲ありに限定しているのはこのため |
| 生成の非同期化 | 192 秒は本番のエッジ(Cloudflare、約 100 秒)を超えるため、**`POST /api/generate` を非同期化した**(下記) |

#### 生成の非同期化(2026-08-09 追加)

`POST /api/generate` が LLM の完了まで待つ同期 API だったため、web_search を入れると必ずプロキシタイムアウトに掛かる。受付と本体を分けた。

- **受付**(`acceptGeneration`): LLM を呼ぶ前に `status = 'PLANNING'` のタスク行を作って即座に返す(実測 0.005 秒)
- **本体**(`completeGeneration`): LLM → プランをタスクに書き込み → Suno 送信 → `provider_task_id` を埋めて `PENDING`。失敗したら必ずタスクを `FAILED` にしてから再送出するので、投げっぱなしの呼び出しでもエラーが進行状況の画面に出る
- **スキーマ変更はしない**。`provider_task_id` は `TEXT NOT NULL` なので、送信前は空文字列 + `PLANNING` で区別する。ポーラーの `listActiveTasks()` から `PLANNING` を除外して `getTask("")` を叩かないようにする
- 起動時に `PLANNING` のまま残っているタスクは `FAILED` にする(LLM 呼び出しは再開できない)
- **スケジューラ(`runDaily`)は同期のまま**。サーバー内で動くので HTTP を経由せずタイムアウト制約が無い。~~`POST /api/daily/run` も参照曲が無いため 44 秒のままで変更しない~~ → **2026-08-10 に非同期化**(下記)
- API の応答は**キーの形状が不変**で `status` の値が 1 つ増えるだけなので、旧アプリでもデコードは通る(ラベルが英語のまま出る)

#### `POST /api/daily/run` の非同期化(2026-08-10 追加)

毎日の自動生成が参照曲ベースになり、「参照曲が無いから 44 秒のまま」という据え置きの前提が崩れたため、こちらも受付と本体に割った。`scheduler.ts` の `runDaily()` を **`startDailyRun()`(受付 = 参照曲の選択 → 冒険判定 → ニュース取得 → `acceptGeneration()`。`complete()` を返す)** と本体に分け、`runDaily()` はその 2 つを続けて呼ぶ薄いラッパにした。

- **スケジューラは `await complete()` のまま**。サーバー内で動きタイムアウト制約が無く、順次生成と `last_daily_count` の記録の正しさもこれで保たれる
- **`POST /api/daily/run` は受付直後に 201 を返し**、本体は `void complete().catch(() => {})` で走らせる(実測 0.03〜0.19 秒)。失敗は `completeGeneration` が必ずタスクの `FAILED` に記録するので、投げっぱなしでもエラーが進行状況に出る
- **レスポンスのキーの形状は変えない**(`{ task, adventure }`。参照曲ベースでは `adventure` は常に `false`)ので旧アプリでもデコードは通る → 同日中の冒険日削除で `{ task }` になり、この互換は捨てた
- ニュース取得(数秒)は受付側に置く。受付が数秒かかっても 100 秒の壁には遠く、失敗しても生成は続行する既存の挙動を変えない
- クライアントは待機表現をやめ、受付後すぐ進行中カード(`PLANNING` = 「曲を考えています…」)に引き継ぐ。iOS は `runDaily()` の 180 秒タイムアウト指定を外した(既定の 60 秒で足りる)

#### 曲名からの登録(2026-08-09 追加)

参照曲を登録する入口がアーティスト名の検索しか無く、「この曲みたいな曲を作りたい」と思ったときに **アーティスト名を思い出す → 登録 → 最大 200 曲から目当ての曲を探す** という遠回りを強いていた(アーティスト名が分からない曲はそもそも入口に立てない)。そこで曲名で検索して曲を直接登録できる入口を足した。生成ロジック(`llm.ts` / `generation.ts` / `scheduler.ts`)と DB スキーマは不変更で、`artist_songs` に行を足す経路が増えるだけ。

| 項目 | 決定 |
|---|---|
| アーティストの逆引き | 曲検索(`entity=song`)の track 行に `artistId` が入るので**検索の 1 リクエストで完結**する(追加の問い合わせが要らない)。よって曲名検索とアーティスト名検索を UI 上で並べても、通信量は変わらない |
| 登録するアーティスト名 | **`lookup` の artist 行の正式表記を使う**(track 行の `artistName` は使わない)。`country=JP` の曲検索では表示名がローカライズされて返る(`artistId` 3296287 = 「クイーン」、530814268 = 「米津玄師」、Official髭男dism)のに対し、`entity=musicArtist` の検索と `lookup` の artist 行は正式表記(「Queen」「Kenshi Yonezu」「OFFICIAL HIGE DANDISM」)。理由は 2 つ — ①既存のアーティスト名検索経路と同じ名前になり `artists.name` の UNIQUE が効いて二重登録(「Queen」と「クイーン」が別行)を防げる ②`llm.ts` の固有名詞混入チェック(`containsName(body, ref.artist)`)は `artists.name` を**英語の** style / title / lyrics から探すため、「クイーン」で登録すると "Queen" の混入を検出できなくなる |
| 候補から選ばせる | カバー・ピアノ版・オルゴールのノイズが多い(「Lemon」の上位 10 件で本家の米津玄師は 2 行だけ、「ボヘミアンラプソディ」ではクイーン本家が上位 5 件に入らない)。アーティスト名検索と同じく候補一覧から選ばせる。`limit` は 25 にして本家が埋もれにくくする |
| 候補の重複除去 | 同一アーティストの同一曲名が複数版返る(クイーンの `Bohemian Rhapsody` が Greatest Hits / Jewels / A Night At The Opera 等で 4 行)。`(artistId, 正規化した曲名)` で畳むと 25 件 → 18 件。既存 `fetchSongs()` と同じ規則(trim + 小文字化・最古のリリースを残す)を使い、並びは iTunes の関連度順(初出の位置)を保つ |
| 日本語検索 | 使える(「レモン」→ 1 位が Lemon / 米津玄師、「夜に駆ける」→ 1 位が YOASOBI)が、読みマッチのため曲名が一致しない行(「感電」「パプリカ」)も混ざる。候補行には**曲名とアーティスト名の両方**を出す。`attribute=songTerm` は付けても結果が変わらなかったので付けない |
| コラボ曲 | track 行の `artistId` は片方のものだけ(「打上花火 / DAOKO×米津玄師」→ Daoko。その `lookup` に「打上花火」も含まれるので整合はする)。登録先が候補の表示名と違う場合は登録後のメッセージで明示する |
| 選んだ曲の確実な登録 | `lookup` は 200 件で頭打ち(米津玄師は JP で 162 track、Queen は 200 で打ち切り)で選んだ曲が漏れうるため、**選んだトラックは必ず個別に `INSERT`** する。曲名は大小文字だけ違う重複行ができないよう正規化して既存行を探してから足す(`artist_songs` の UNIQUE は BINARY 照合のため) |
| アーティストの曲も全部取り込む | 曲名から登録する場合も、そのアーティストの曲(最大 200 曲)をまとめて取り込む。正式名とジャンルを取るために `lookup` はどのみち 1 回必要で、曲一覧は同じ応答に入っており追加コストがゼロのため |
| API 設計 | `GET /api/artist-songs/search` と `POST /api/artist-songs` の追加のみ。`POST` の body は `{ itunesTrackId }` だけにして**クライアントの申告は信用せずサーバーが `lookup` で取り直す**。アーティストが登録済みなら追加の `lookup` を打たない。パス名は `artist_songs` テーブルに合わせ、生成曲の `/api/tracks` と紛れる `/api/songs` は避けた |
| iOS の導線 | **生成タブに「曲名から生成」の行を新設**する(アーティスト追加シート内のモード切り替えにはしない)。曲名しか知らない人が「アーティスト」を 2 回通る導線になり、この機能の動機と噛み合わないため。管理画面は画面数を増やさず登録パネル内の切り替えにした |

### 思考の深さ(effort)の切り替えとモデル表示(2026-08-10 追加)

生成の頭脳が何なのかが管理画面から分からず、品質・コスト・所要時間を動かすつまみも無かった。Claude の `output_config.effort`(GA。`low` / `medium` / `high` / `xhigh` / `max` の 5 段階)を設定ページから切り替えられるようにし、あわせて使用モデルを表示した。

| 項目 | 決定 |
|---|---|
| モデルの扱い | **読み取り専用の表示**。`LLM_MODEL` / `SUNO_MODEL` は `.env`(本番は環境変数)が真実源で、DB 設定にすると二重管理になりどちらが効いているか分からなくなる。存在しないモデル名を画面から保存できてしまう問題も避ける |
| effort の保存先 | `settings` テーブルの `llm_effort`。既定は `high`(API の既定と同じなので、設定が無い既存 DB でも挙動が変わらない)。生成のたびに読むステートレス方式で、変更は次の生成から即反映 |
| 適用範囲 | 全モード共通(daily / manual / artist)。参照曲あり/なしでの出し分けはしない |
| `max_tokens` | **16,000 → 32,000 に拡大**。`max_tokens` は思考と本文の合算の上限で、effort を上げると思考がこの枠を食う。実測で effort=max の出力は 15,639 と 20,139 トークン(同じ設定でも振れ幅が大きい)で、**旧上限では 2 曲目が切れていた**。切れると JSON が途中で終わり `JSON.parse` に失敗してタスクが `FAILED` になる |
| 呼び出し方 | **ストリーミング(`messages.stream().finalMessage()`)に変更**。TypeScript SDK は `max_tokens` が **21,333**(`60分 × max_tokens ÷ 128000 > 10分`)を超える非ストリーミング要求を「10 分を超える恐れ」として**送信前に例外**にする(クライアントに明示 timeout がある場合のみ回避される)。実測で発覚 — 32,000 のままでは全生成が失敗する。応答の扱いは `finalMessage()` で非ストリーミングと同じで、`web_search` の server tool ブロックも同じように積まれる(実測: ツール呼び出し 10 回を検出、入力 141,514 トークンで完走) |
| 観測 | 生成のたびに使用モデル・effort・`stop_reason`・入出力トークン数をログに出す(上限に対する余裕が運用中に見える) |

### 毎日の自動生成を参照曲ベースに変更(2026-08-10 追加)

毎日の曲はプリセット要素プール + ニュースから LLM が自由に組む方式だった。一方 2026-08-09 に入れた参照曲ベースの生成(`artist`)は `web_search` で実際の BPM・キー・コード進行・編成を調べてから style を書くため、生成物が「それっぽい音楽用語の羅列」ではなく実在の曲の構造に裏付けられる。ただし手動の入口からしか使えなかった。**毎日の曲もこちらに乗せ替えた**。`llm.ts` の web_search 有効化条件は当初からモード名ではなく `referenceSong` の有無で判定していたため(2026-08-09 の設計判断)、参照曲を渡すだけで検索は効いた。実作業の中心は「誰がどの曲を選ぶか」と「`POST /api/daily/run` の非同期化」。

| 項目 | 決定 |
|---|---|
| 切り替え範囲 | **1 日の全曲を参照曲ベースにする**。登録曲が 0 件のときだけ現行のプリセット方式へフォールバック(警告ログを出す)。毎日の生成が止まらないことを優先する。プリセットの 👍/👎 学習ループは daily から外れるが、その後始末は別 TODO で扱う → **同日中に実施し、フォールバックごと廃止した**(下記) |
| 曲の選び方 | **サーバーが選ぶ**(LLM には選ばせない)。実装が最も単純で、出力スキーマの追加も照合も要らない |
| 選択の規則 | **①ノイズ除外 → ②アーティストを LRU で選ぶ → ③その人の曲を LRU で選ぶ**の 2 段階(`server/src/reference.ts` の純関数)。曲一様ではなく**アーティスト一様**にするのは、取り込みが 1 アーティスト最大 200 曲でカタログの大小差が桁違いなため(実測 78 / 122 / 95 曲)。LRU(未使用 → 最終使用が古い順のグループから一様ランダム)なら「直近 N 日は除外」のような設定を増やさずに、連続回避・枯渇回避・一巡が同時に成立する |
| ノイズ除外 | 曲名の**括弧書き・ダッシュ以降の注釈部分だけ**を見て `Live` / `Remix` / `Instrumental` / `Karaoke` / `Cover` / `Acoustic Ver` / `Remastered` 等を含む曲を候補から外す。本題側を見ないのは「Live and Let Die」「Cover Me」のような原曲を落とさないため。**除外した結果 0 件になるなら除外しない**(小さいカタログを空にしない)。実測では OFFICIAL HIGE DANDISM の 161 曲から 66 件(すべて LIVE / Instrumental / Acoustic Ver の別バージョン)が正しく外れた |
| 同日 3 曲の重複回避 | **受付(`acceptGeneration`)の時点でタスク行に `artist_song_id` が入る**ため、2 曲目の選択時には 1 曲目が「使用済み」として見える。結果その日の 3 曲は自動的に別アーティスト・別曲になる(実測: 3 連続で 3 アーティストがきれいに一巡)。専用の除外リストは持たない |
| 今日のコンテキスト(ニュース) | **注入する**。曲調は参照曲、歌詞のテーマは今日のニュースから採る。「毎日違う曲が届く」性格とリアルワード制限の意味が保たれる。参照曲とニュースが同時に来るのは新しい組み合わせなので、作り方の節に優先順位を 1 行足した(「音はリファレンス・言葉はコンテキストを優先する」) |
| 冒険日 | **daily からは外す**(`mode` は `daily` 固定)。「参照曲に似せる」目的と「大きく外す」指示が矛盾するため。`adventure_probability` はフォールバック経路でのみ生きる(設定画面に注記)→ フォールバックごと同日中に廃止 |
| プロンプト分岐 | `llm.ts` の分岐 5 箇所を `mode === "artist"` から **`referenceSong` の有無**へ寄せた(リファレンス節 / 要素プール節 / 直近スタイル / 禁止ワードの注記 / 歌声の指示)。とくに `planIssues()` の固有名詞チェックはモード名判定のままだと daily の曲だけ検査を素通りし、検索結果由来の固有名詞がそのまま Suno の `SENSITIVE_WORD_ERROR` を踏む(同日中の削除で参照曲が必須になり、分岐そのものが消えて直線になった) |
| DB スキーマ | **変更なし**。`tasks.artist_song_id` は 2026-08-09 に記録だけ先に用意してあり、候補一覧(`db.listReferenceCandidates()`)はその最新 `created_at` を LRU の基準に使う |
| 表示 | `mode = 'daily'` のままで、参照曲は既存の `ref_artist_name` / `ref_song_title` で表現される(管理画面も iOS もモードで出し分けていないため表示側の改修は不要)。タスク一覧の `prompt` は `毎日の自動生成 / <アーティスト>「<曲名>」風` |
| コストと所要時間 | 1 曲約 $0.36 × 3 曲 = **約 $1.1/日(月 $33 前後)**、従来の約 9 倍。朝の実行は 1 曲 3〜4.5 分 × 3 曲で 10〜14 分になる(`tick()` の `ticking` ガードで多重実行はしない。Suno のポーラーは別ループなので 1 曲目の完成待ちと 2 曲目の LLM 生成は並行する) |

`POST /api/daily/run` の非同期化も同時に行った(下記)。実測(参照曲 = OFFICIAL HIGE DANDISM「愛なんだが…」+ 地震のニュース)では、検索 12 回・入力 119,720 トークンで style に `92 BPM in D major` が入り、`sources` 5 件(tunebat / Spotify / Apple Music)、intent が「検索で確認した実データ」と「作風からの推定」を書き分け、歌詞にはニュース由来の情景(ラジオのニュース・揺れ)が乗った。

### 参照曲ベース化で使われなくなった機能の削除(2026-08-10 追加)

上の切り替えで、それまで毎日の曲を組み立てていた仕組み(要素プール・評価学習・冒険日・直近スタイル注入)は**登録曲 0 件のときのフォールバックにしか残っていない**状態になった。切り替え時は撤去を範囲外にしていたが、同日中に洗い出して**すべて削除した**。「使われていない」の根拠はコードから確認できる事実に揃えた — ①プロンプトの分岐は `referenceSong` の有無で決まるため、参照曲があると要素プール節・直近スタイル節・冒険日節は一切出ない ②冒険日は `!reference && Math.random() < ...` で参照曲があると構造上ゼロ確率 ③要素プールが提示されるのは「参照曲なしの daily」だけで `manual` 分岐は見ない ④`manual` の `selectedPresets` を埋める `presetIds` を送るクライアントが 1 つも無い ⑤評価集計の LLM 注入は 1 箇所だけ = 参照曲があると 👍/👎 は生成に一切影響していない。

| 論点 | 決定 |
|---|---|
| 参照曲 0 件のフォールバック | **廃止**。候補ゼロなら生成せず `NoReferenceSongError` を投げる。スケジューラは既存の失敗処理に乗って 30 分後に再試行し(`last_daily_*` を進めないのでアーティストを登録すればその日のうちに追い生成される)、`POST /api/daily/run` は **409** を返す |
| 👍/👎 評価 | **完全廃止**(UI・API・`tracks.rating` / `rated_at` カラムまで)。参照曲ベースでは生成に影響しないため、残すと「評価しているのに何も変わらない」UI になる |
| カスタム生成(`mode = manual`) | **廃止**。`POST /api/generate` は `artistSongId` 必須(未指定は 400)。**自由テキスト(`freeText`)は残す** — 管理画面の `artists.js` が参照曲生成に「追加の要望」として添えて送っているため。消えるのは「自由テキストだけで作る経路」 |
| 過去データの表示・旧アプリ互換 | **どちらも捨てる**。冒険日バッジ・使用プリセット表示を削除し、`POST /api/daily/run` 応答の `adventure` キーも削除。旧アプリは新サーバーで動かない(`DailyRunResponse.adventure` が非 optional のためデコードが失敗する)ので、サーバーと実機アプリは同時に更新する |
| パラメータ一覧ページ | **ページごと削除**(`presets.html` / `presets.js`)。`GET /api/real-world-words` も道連れ(利用者はこのページだけ)。リアルワードの状況は iOS の生成パラメータ画面で見られる |
| DB のテーブル | **DROP する**(`presets` / `task_presets` / `profile` + `tracks.rating` / `rated_at`)。起動時の一回限りの後片付けで、`DROP ... IF EXISTS` とカラム存在チェックにより冪等なので `settings` への実施記録は持たない。`settings` の `adventure_probability` / `migration_drop_instrument_presets` も削除する |

削除から導かれる構造 — 生成モードは `daily` と `artist` の 2 つだけになり、どちらも必ず参照曲を持つ。`SongPlanInput` は `{ instrumental, freeText, extraContext?, referenceSong }` に縮み(`referenceSong` は必須)、`buildSongPlanPrompt()` は分岐の無い直線(リファレンス → 作り方 → 追加の要望 → 今日のコンテキスト → 禁止ワード → 残り 1 回 → 出力条件)になり、`web_search` は常時有効、固有名詞チェックは無条件になった。`instrumental` は非目標として残した(カスタム生成の削除で常に `false` になるが、API の受け口・DB カラム・Suno への引き渡し・過去データの表示に関わる別系統の機能のため)。

## API(追加)

- ~~`GET/POST/PUT/DELETE /api/presets`~~ — プリセット管理(2026-08-08: 各プリセットに評価集計 `upCount` / `downCount` を付与。2026-08-10 廃止)
- ~~`GET /api/profile`~~ — 現行プロファイルの閲覧(2026-08-08 廃止)
- `GET/PUT /api/settings` — 設定(毎日の自動生成+外部コンテキスト+リアルワード制限)。2026-08-10 追加: `llmEffort`(変更可)と `llmModel` / `sunoModel`(読み取り専用。`PUT` では受け付けない)。キーの追加のみで既存キーの形状は不変のため、旧 iOS アプリのデコードは通る
- ~~`GET /api/real-world-words`~~ — 直近ウィンドウ内のリアルワード使用状況(パラメータ一覧ページ用。2026-08-10 にページごと廃止 — 状況は `GET /api/generation-params` で見られる)
- `GET /api/generation-params`(2026-08-09 追加)— おまかせ生成が LLM に注入する入力の一覧。iOS の生成パラメータ画面用で、runDaily と同じ関数群から組み立てることで表示と実際の生成入力のずれを防ぐ。当初は冒険日確率・評価集計付き要素プール・直近スタイル(和訳付き)も返していたが、2026-08-10 の削除で **`referenceCandidates`(アーティスト名・ノイズ除外後の候補曲数・最終使用日時。次に選ばれやすい順)/ `recentReferences`(直近に参照した曲)/ `contextNews` / リアルワード制限(`wordMaxUses` / `wordWindowDays` / `bannedWords` / `lastChanceWords` / `trackedWordCount`)**だけになった。`referenceMode` も削除 — フォールバックが無くなり分岐の意味が消えたため(候補が空 = おまかせ生成できない、という表示になる)
- `POST /api/daily/run` — 自動生成の手動トリガ(管理画面・iOS のおまかせ生成が使用)。2026-08-10 変更: 受付だけ済ませて 201 を返す非同期方式に。同日中に応答キーを `{ task }` に変更(`adventure` を削除)し、参照曲が 1 件も無いときは **409** を返すようにした
- `POST /api/generate` — 参照曲(`artistSongId`、**必須**)+ 任意の追加要望(`prompt`)+ `instrumental` を受け、`mode = 'artist'` で生成する。2026-08-09 に `artistSongId` を追加、2026-08-10 に必須化(未指定は 400)— それまでは `presetIds` + 自由テキストのカスタム生成(`mode = 'manual'`)も受け付けていた
- `GET /api/artists/search`・`GET|POST /api/artists`・`GET /api/artists/:id/songs`・`POST /api/artists/:id/refresh`・`DELETE /api/artists/:id`(2026-08-09 追加)— アーティスト管理。登録は iTunes からの楽曲取り込みまで行い、`refresh` は差分のみ追加、削除はアーティストと曲を消す(生成済みタスクはスナップショットで表示継続)
- `GET /api/artist-songs/search`・`POST /api/artist-songs`(2026-08-09 追加)— 曲名からの登録。検索は iTunes の曲候補(`itunesTrackId` / 曲名 / 表示用アーティスト名 / アルバム / 年)を返すだけで DB に触らない。登録は body `{ itunesTrackId }` のみで、曲メタをサーバーが取り直し、未登録のアーティストは正式表記で同時に登録して曲も取り込む。応答の `song.id` をそのまま `POST /api/generate` の `artistSongId` に使える
